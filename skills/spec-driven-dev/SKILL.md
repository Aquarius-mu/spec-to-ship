# 飞书方案驱动实现

> 文中出现的消息名（`Cmd_Xxx_CS`）、结构体名（`CmdRankRoleItem`）、文件名是 **DemoSvr 示例**。
> 换项目时对应物见 `spec-to-ship/references/profile/<项目>.md` §四，规则本身不变。

**范围**：案子 → 代码。入口是需求清单，出口是"每条 R-xx 都有 file:line"。
**不负责**：读飞书（`case-reader`）、协议怎么定义（`game-message-protocol`）、怎么验收（`adversarial-gameplay-acceptance`）。

---

## 铁律

1. **案子是唯一权威**。skill / memory / 参考实现只决定"怎么做"，不决定"该不该有"。
   - 周期、单位、命名必须来自本案子。实踩：排行榜玩法是"每轮独立"的榜，照抄二期"周榜"命名 `RankSeasonWeek`，被指出周期错。
2. **能自己查到的，不许问**。案子原文、策划表、公共配置、现有代码、协议定义、历史台账——先查完再判断。
3. **查不到的**：写「回退方案 + 日志」继续做，在交付说明标出；不阻塞、不反复问。
4. **每个字段必须写出消费方**，写不出就删。
5. **接线不算实现**。注册 handler、加字段、调函数都要打开实现确认语义覆盖。

## 流程

### 1. 接需求清单

先看 `.tmpfiles/<功能>/需求规格.md`：

| 状态 | 动作 |
|---|---|
| 已存在 | 直接读，沿用 `R-xx` 编号，**不重读飞书** |
| 不存在 | 派 `case-reader` 生成（它负责正文/画板/内嵌表/评论/空章节） |

编号统一 `R-xx`，永不复用；空章节记一条「章节为空」。
需要开工五张表（状态/ID/上限/推送/消息契约）→ 走 `game-feature-playbook`，不在这里重复。

### 2. 字段映射（凡方案画了界面、列了表头，必做）

先把案子里该界面列出的每一条落成表，再写码：

| 案子字段 | 文本id | 协议字段 | 数据来源 | 结论 |
|---|---|---|---|---|
| 公会 | STRID_COCMap_Guild | vRank[].sGuildName | stBaseInfo.sGuild | 已实现 |
| 击杀士兵数 | STRID_COCMap_KilledSoldiers | vRank[].iRankValue2 高位 | RankItemInfo.iKillSoldier | 已实现 |

**判据**：每行有结论，"缺"的行数必须为 **0** 才允许交付。
数据来源要写到具体结构体字段，不能写"已有接口"。

> **只按代码现状补（"这里少个字段"）不算做过需求。** 必须先按案子列出的字段逐项核，再回代码找缺口。
> 实踩：排行榜玩法排行榜案子明列 6 列，直接读代码发现 `CmdRankRoleItem` 联盟为空就去补，没先对照案子，被指出"案子明明写了，为什么还是没有"。

**全新功能时**：代码侧没有落点，这一步先产出「新增字段清单」，等 `game-message-protocol` 定完 CmdId 与结构体名再回填映射表。不要卡在硬填。

### 3. 消息与存储：先做减法

按顺序问，任一是就删：

1. **客户端能不能用已有字段算出来？**
   `bStartSoon` = `iStageEndSec - now <= 180`；胜负 = `iWinnerGuildId != 0`；列表条数 = `vList.size()`
2. **策划表里有没有？** 名称/奖励/上限/消耗/概率 → 客户端读表
3. **别的消息是否已下发？** 排行榜走通用榜 `Cmd_Rank_Role_CS`；道具数量走 `Cmd_Push_SetItem`
4. **是不是客户端自己刚发的回显？** 只有多 `iType` 复用同一条 SC、或分页时才保留
5. 只有 1–4 全否（服务端权威既成状态）才下发

**其他硬规则**
- `iTotal/iOffset` 只在真分页时保留；≤ 十几条的固定列表不分页
- 操作码用 `enum`，禁裸数字；服务器自己的动作（刷新快照、修正状态）走内部函数，不塞进 CS 值域
- 状态类数据收进结构体挂 Status，禁止平铺一堆同前缀字段
- **同一份数据只有一个来源**
- **上行同理**：CS 里客户端"知道自己刚发了什么"的计数/结果不回传

### 4. 存储只存服务端要用的

- 同 key 的多份状态合并成一个子结构（`map<id, {type, flag}>`）
- 能由配置/时间算出的阶段不落盘
- 只读一次不再用的中间量不持久化
- **没外放就压实 tag**：每删一个字段立刻重排 0..N 连续，不留空号，改完跑脚本校验重号/跳号

### 5. 按 UI 形态决定 push 还是 Status

- 常驻展示（悬浮窗、倒计时、进度条）→ 进 Status 或查询回包，push 只做实时刷新
- 一次性事件（飘字、动画、单场战报）→ 只 push，但要有查询入口可回查
- 红点 → 客户端用已有数据自己算，服务器不下发

### 6. 服务端编排的自动战斗（仿参考玩法）四条

1. **每个战场各存一份队列快照**。同一支防守队会被两个进攻阵营同时打，共享指针会串场
2. **同一玩家串行**。一人多队可能同时进两个战场，而 GameServer 战斗上下文只有一份
3. **超时重试，不直接判负**。仿 `BattlefieldMap::startFight` 的 `iNoResultNum`/`iTimeoutMs`
4. **开赛留缓冲再快照**。各 GS 要先撤采集/补兵/刷镜像，跨服快照晚于开赛几秒；等 10s 再建队列，重启沿用已落盘队列

### 7. 逐条实现

消息优先：先定 CS/SC/Push/GF/FG 与字段，再写逻辑。
顺序按玩家旅程：入口 → 准备 → 进行 → 结算 → 清理。
代码质量硬规则（消息减法、文件不拆、头文件要减、注释精简、改动覆盖需求单全部提交）→ 读 `spec-to-ship/references/code-quality.md`。
本仓库物理陷阱（unity build、协议号、0 哨兵、跨区 key）→ 读 `spec-to-ship/references/codebase-pitfalls.md`。

### 8. 双 agent 独立审查

派两个只读 agent，各自读「需求清单 + 代码」：

| Agent | 任务 | 输出 |
|---|---|---|
| **A 需求覆盖** | 逐条核对 `R-xx → file:line` | 已实现 / 未实现 / 偏差 |
| **B 玩家预演** | 以玩家身份从进活动走到结算，逐步问"此刻客户端能拿到什么、服务器做了什么" | 走不通处即断点 |

每条必须有复现路径，不接受"建议加强"。**P0 断点清零才交付。**

### 9. 自己先当玩家走一遍

进活动 → 设队 → 开打 → 看战况 → 看排行 → 结算。每一步问「这个数值/名称和案子对得上吗」。
实踩：`iAttackTeamNum` 返回总队数而不是剩余队数、排行榜周期命名错，都是这一步能查出来的。

## 自检 10 条

CS 有且仅回一条 SC ｜ push 有消费方 ｜ **常驻 UI 有首屏来源** ｜ **每个字段能说出消费方** ｜ **能推导/查表/别处已发的一律不下发** ｜ **操作码用枚举、内部操作不进 CS** ｜ **同 key 状态合并、可算的不落盘** ｜ **未外放改完压实 tag（0..N 无空号）** ｜ **短列表不分页** ｜ 状态有清理 ｜ 扣费有退款 ｜ 跨服有回投 ｜ 边界（0/满/离线/超时/换轮/赛季末）有分支 ｜ **方案 UI 字段逐项 → 协议字段有映射表** ｜ 交付带覆盖表

## 反模式

片段读案子 ｜ **不读案子先看代码，按代码缺口补需求** ｜ **方案列了字段清单却不做逐项映射** ｜ 把接线当实现 ｜ **常驻 UI 只靠 push** ｜ 服务器下发红点 ｜ **活动 SC 里塞排行榜/奖励预览/倒计时提示** ｜ **把客户端能算的派生值当字段发** ｜ **回包带客户端自己发的计数** ｜ Status 平铺同前缀字段 ｜ 静默降级 ｜ 自己审自己 ｜ 不给覆盖表
