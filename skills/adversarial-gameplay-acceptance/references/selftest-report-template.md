# 靶场实跑报告模板

> 案头审计报告用 `report-template.md`；**这份是"真的把消息发出去过"之后写的**。
> 两者的区别只有一条：这里的每条结论后面都要挂一个**能复现的证据**。

---

```markdown
# <功能名> 靶场实跑报告

## 0. 环境指纹
（本次结论成立的前提，格式见 `environment-intake.md` §三。缺这一节报告不予交付。）

- 代码版本   : <revision / 本次改动范围>
- 二进制部署 : <部署时间，取自日志首行或发服记录>
- 环境名     : <dev / 云 / 外网 / 预发>
- 目标实例   : <区服 / 跨服实例 / 进程>
- 测试角色   : <uid / account>
- 关键数据态 : <名单是否已重建 / 角色是否已加载进内存 / 相关开关与阶段状态>
- 探针       : `<探针目录>/<脚本名>.lua`（`tmp_` 前缀的为临时）

> 环境不对，结论全部作废。dev 的结论不能推到外网。
> **关键数据态那一行最容易漏、也最值钱**——大量"看起来像 bug"的现象最后归到数据态。

## 1. 断言表（来源：<需求文档名 + 章节>）

| # | 断言 | 来源 | 结果 | 证据 |
|---|---|---|---|---|
| A1 | 开启后返回分区 ID | 2.1.2 | ✅ PASS | `iDistrictId=1` |
| A2 | 名单满 32 人 | 2.1.2-5 | ⚠️ 环境 | 测试服无常规赛历史，GM 塞人后为 32 |
| A3 | 非布阵窗口设置阵容被拒 | 2.3.1 | ❌ FAIL | 回 0 且阵容已改（见发现 F1） |

结果口径：**✅ PASS**（实测符合）｜**❌ FAIL**（实测不符，必须给定位）｜
**⚠️ 环境**（失败原因是测试环境缺数据，不是代码）｜**⬜ 未覆盖**（写了为什么没测）

## 2. 三路取证

对每条 FAIL / 可疑项，把下面三路摆出来对照：

| 取证路 | 手段 | 本次结果 |
|---|---|---|
| ① 玩家看到什么 | 探针回包 / 推送 | <关键字段实测值> |
| ② 服务端真实状态 | GM 查询 / 数据库（**查权威那台，不是镜像**） | <状态机/名单/结算的真实值> |
| ③ 流水与库 | `log --kind alarm` / mysql 查询 | <相关日志行 or 表字段> |

> **两路打架 = 还没查完。** 比如回包说"已领取"、GM 查出来标记没置位，
> 那就是"回了假成功"，比不回包更毒。

## 3. 发现

### F1 <一句话结论> ｜P0/P1/P2 ｜**已实测复现**
- **玩家场景**：<什么操作 → 看到什么 → 应该看到什么>
- **定位**：`文件:行号`
- **复现**：`selftest.py run <探针> --uid N --zone N` → <回包片段>
- **反证**：<GM 查出来的真实状态 / 日志行>
- **建议**：<改哪里>

> 每条发现都要有"复现命令 + 实测输出"。**没跑过的结论写进第 5 节，不写这里。**

## 4. 玩家旅程实测记录

按真实时序走一遍，记录每一步的实际反馈（这是最容易发现"断链"的地方）：

| 步骤 | 操作 | 实际反馈 | 该有的反馈 | 判定 |
|---|---|---|---|---|
| 1 | 进主界面（GetInit） | 分区/阶段/名单全下发 | 同左 | ✅ |
| 2 | 设置阵容 | 回 0 | 回 0 + 状态同步 | ✅ |

## 5. 未实测项（不许留白，不许用空话敷衍）

| 项 | 为什么没测 | 风险 |
|---|---|---|
| 客户端渲染 | 服务端看不到 | 需客户端确认弹窗时机 |
| 真实多人交互 | 靶场只有单人 uid | 需 QA 多角色环境 |

## 6. 结论

- 通过 N 条 / 失败 M 条 / 未覆盖 K 条
- **可上线**：<是/否>，阻塞项：<F1…>
- 下一次要补的：<环境数据 / 多人场景 / 客户端确认>
```

---

## 写报告的两条硬规矩

1. **区分"跑过"和"想过"。** 第 3 节的发现必须有复现命令；只靠读代码推出来的，放回案头审计报告。
2. **环境问题要标明。** 测试服缺数据导致的失败（如没跑过常规赛 → 候选池空）**不是代码缺陷**，
   标成 `⚠️ 环境` 并写清"要验它得先造什么数据"，别混进 bug 列表浪费排期。
