# 多 Agent 标准化验收编排（形态 B 的规模化）

> 适用判据：验收清单条目多（≥30）、玩家身份不止一种（参赛者 / 观众 / 跨服多方）、
> 或存在"别人操作影响我反馈"的多人交互（别人下注、别人参战、别人顶替）。
> 不满足就单线程跑，别为编排而编排。

主 agent 是**验收总指挥**，只做五件事：定清单、分派、定时序表、闭环督办、合并汇报。
所有实测动作全部下放子 agent，主 agent 不抢子 agent 的活。

---

## 靶场能力盘点（开工前逐项确认，缺哪项先补或降级）

| 能力 | 用途 | 缺了降级为 |
|---|---|---|
| ① 消息探针 | 模拟客户端发 CS、收 SC/推送 | 只能 GM 驱动 + 读码推断 |
| ② GM 通道 | 造状态、查服务端真实值 | 手动凑环境，慢且不可重复 |
| ③ 日志 | 实时日志/埋点取证 | 事后拉日志文件，时序对不上 |
| ④ 数据库 / 缓存 | 造环境、核权威态 | 只能信 GM 回执（回执 ≠ 生效） |
| ⑤ 编译 + 发布 | 修码后发服复跑 | 案头审计，FAIL 无法闭环 |
| ⑥ 需求文档 | 「正确期望表现」唯一权威源 | 用户口述边界，覆盖面靠人记 |

这六样就是 `target-range-adapter.md` 的六件套。**每样落到哪个命令、哪个 URL、哪个账号，
写进本团队的 `project-anchors.md`**——第一次接完就固化，下次开工不重新摸。

六项齐 = 可全量编排。缺编译/发布 = 阶段 3 闭环断，只能出报告等用户发服；
缺探针 = 玩家 agent 无法实跑，降级为驱动 agent + 日志/回执取证。
工具入口（命令、URL、账号）沉淀进 `project-anchors.md`，下次开工不重新找。

## 标准流水线（五阶段，顺序不可乱）

```
阶段0 清单先行 ──► 阶段1 双准备(并行) ──► 阶段2 按身份分派实跑
                                                │
                    ┌───────────────────────────┘
                    ▼
              阶段3 FAIL 修复闭环（修码→复审→发服→复跑，循环到 PASS）
                    │
                    ▼
              阶段4 全员终态后合并报告
```

## 阶段 0：模拟验收清单先行（没清单不许开工）

**先列清单、写死正确期望表现，再分派。** 这一步防的就是"傻傻跑"——只测了主流程
（战斗、赛事驱动），消息推送、客户端模拟、示例玩法、边缘功能全漏掉。

**覆盖面铁律：以消息清单为纲，不以主流程为纲。**

- Step 0 消息清单里**每条 CS/SC、每条 Push、每条 Forward** 至少一条验收条目。
- 边缘功能（示例玩法下注、红点、邮件、回放、榜单、每日刷新……）逐个对号入座，
  对不上号的就是漏项，当场补进清单。
- 需求文档每条需求至少映射一条条目；文档有而消息没有的，标"需客户端确认"。

**清单模板**（一行一条，条目 ID 全局唯一，按角色分组前缀）：

| 字段 | 说明 |
|---|---|
| 条目 ID | 组前缀-序号，如 GA-1 / GB-7 / GC-3 |
| 身份角色 | 该条目由哪种身份的玩家/驱动方触发 |
| 前置 | 阶段状态、角色状态、数据准备 |
| 操作 | 发哪条消息 / 触发哪个 GM / 等待哪个时间点 |
| **正确期望表现** | 从需求文档原文抄，标注来源章节号；**禁止 agent 自己脑补预期** |
| 取证方式 | 回包 / GM 查状态 / 日志，三路中选哪几路 |
| 状态 | PENDING / PASS / FAIL / ⚠️环境阻 / 需客户端确认 |

**没写正确期望表现的条目不许分派**——子 agent 拿不到预期就会把实际行为当正确行为放过。

**清单评审闸门（治需求理解偏差）**：清单写完、分派之前，把清单给用户过目一次——
这是整个流程**唯一一次开工确认**，重点确认「正确期望表现」列。理解偏差 90% 出在期望表现
写错而不是跑错；开工后每打断重对一次需求，代价是开工前的十倍。

**歧义预决策表（同闸门一次拍完）**：写清单时发现的文档歧义/缺失（文档没写、截图与正文矛盾、
数值口径两说），列成 `歧义点 | 影响哪些条目 | 拟按哪种字面执行` 三列表，请用户**一次性**拍板。
拍板结果写回对应条目的期望表现。开工后**不再**为新歧义打断用户：按文档字面执行 +
记入「待确认项」继续跑，阶段汇报时批量表出（见「打断控制」）。

**期望可执行化**：期望表现尽量同时写成可机械比对的断言（本项目：`selftest.py check`
的 plan.json，字段=值）。复跑轮次越多，脚本机械比对比 agent 肉眼判定越省越稳，
也消灭"agent 觉得看起来对了"这种主观放行。

## 阶段 1：双准备 agent（并行启动，互不依赖）

| Agent | 职责 | 输出 |
|---|---|---|
| **环境准备** | 编译 → 发服（**先跟用户确认**）→ GM 造数据（推阶段、塞名单、克隆号、补资源）→ 存基线快照 | 可测环境 + 基线（角色属性/名单/状态） |
| **代码盘点**（只读） | 清单条目 ↔ 实现落点映射 | `条目ID \| 文件:行 \| 关键函数 \| 实装/部分/未实装/未找到` 映射表 |

环境准备必须**可重复重造**：把造数动作记成有序命令序列（GM 指令、SQL、redis 操作），
基线快照存档。阶段 3 每轮修码发服后复跑前，**先回基线重造环境**——上一轮跑挂时
名单/阶段/标记已被污染，直接复跑 = 用脏环境验新代码，FAIL 了也分不清是没修好还是残留。

**每个造数动作都要配一个落地判据**（见 `project-anchors.md` 第三部分）：命令返回成功 ≠ 生效。
规模化编排里这条尤其致命 —— **一个没生效的造数动作，会让所有子 agent 的结论一起建在沙子上**，
而且表现得像"功能没实现"。环境准备 agent 交付时附**判据的实际读数**（不是命令回执），主 agent 抽查两项。

盘点表是阶段 3 的分诊依据：跑挂时先查表——**映射表里"未实装/未找到" = 代码问题，
"实装"却挂 = 环境或时序问题**，两条路修法完全不同，不先分诊就是瞎修。
⚠️ 分诊前先过一遍「假 bug 四问」：**"实装却挂"里混着大量假 bug**，
直接归到"环境或时序"就往下修，等于放弃了观测关与数据态关的排查。

盘点 agent 必须只读；明确要求"找不到就写未找到，不许猜"。

## 阶段 2：两级切分——先按三个视角，再按玩家身份

**第一级：三个视角各一个 agent（策划 / 玩家 / QA）。** 见 `SKILL.md` 的「三个身份，各跑一遍」。
**三份清单独立产出，分派时不许互相看** —— 看了就趋同，趋同就漏掉各自盲区。

| 视角 agent | 只关心 | 它的清单从哪来 |
|---|---|---|
| **策划** | 需求文档字面 | 文档每条需求 → 实现落点；答"写了没实现 / 实现了没写" |
| **玩家** | 我点了之后屏幕变没变 | 玩家旅程时间线（下面按身份再细分） |
| **QA** | 边界与异常 | 对抗场景卡逐张打出 |

**第二级：玩家视角再按身份细分**（同一份旅程，不同身份走法不同）：

| 玩家 agent | 扮演谁 | 跑哪些条目 |
|---|---|---|
| **驱动** | GM/时间轴 | 阶段推进、名单重建、结算触发、跨进程聚合、日志表 |
| **参赛玩家** | 名单内角色 | 全程玩家旅程：首屏、编队、下注、收奖励、收推送 |
| **非参赛玩家** | 名单外角色 | 观众视角：默认进组、可否下注、操作拦截、全服奖励 |

**交叉比对由主 agent 做**：同一条目三方结论不一致 = 高价值信号（对照表见 SKILL.md）。
主 agent 合并时专门跑一遍这张比对表，不一致的**重新实测裁决**，不许取多数票。

### 可选但强烈推荐：专职攻击者 agent

**一个 agent，唯一任务是推翻已产出的清单，不许平衡、不许客气。**

```
你是对抗性审查员。你的唯一任务是攻击并推翻下面这份清单。
你要假定它是错的、是残缺的，然后去找证据证明。
**不要客气。不需要平衡。你的价值在于找出它漏了什么、错了什么。**
```

给它四类攻击方向（缺一不可）：

| 方向 | 找什么 |
|---|---|
| **找漏** | 文档里有、清单里没有对应实现的 |
| **找错** | 清单写了、但与文档/代码不符的 |
| **找冗余** | 清单里有、但文档没要求或已有替代的 |
| **撕结论** | 清单里"不需要 / 纯客户端 / 复用即可"这类**否定性结论**——它们最容易错 |

**"撕否定性结论"是价值最高的一类**：一句"这个不需要服务端参与"如果错了，就漏掉整条链路。
攻击者要能给出"它错了"的证据，也能明确说"**攻击失败，这条成立**"——失败也是有效产出。

> 实战效果（本 skill 用过一次）：找漏 7 条、找错 5 条、冗余 2 条，**攻击失败 0 条**；
> 其中三条被判为最致命（缺状态变更推送、入口数据没有来源、跨进程字段不存在）。
> 输出必须带**证据基线**（读了哪些文档/代码），否则攻击结论本身不可信。

给每个验收 agent 的输入必须包含五样：

1. 属于它身份的清单条目（含**正确期望表现**与来源章节）——只给它自己那组，不给全清单
2. 探针工具用法（发消息、收回包、GM 查询、拉日志）
3. 它可用的角色/区服/凭据（与别的 agent 不重叠，防止互踩数据）
4. **行动时序表**：哪个阶段窗口内能做什么，窗口外只准取证不准操作
5. **GM 操作分片**：玩家 agent 只准操作自己名下对象（自己角色、自己测试数据）；
   全局操作（推阶段、重置、重造名单）只归驱动 agent——玩家 agent 一条全局 GM
   就能把别人正在验的场景轰没

**多人交互靠并发**：示例玩法要"别人也在下注"、比赛要"别人先参战"才验得出来——
这正是一个 agent 一个人格的价值。主 agent 在时序表里给交互留并发窗口。

**阶段关卡（barrier）**：时序依赖是主 agent 的责任，固化为关卡——驱动 agent
推进阶段前，主 agent 检查依赖该阶段的玩家 agent 已把该窗口条目全部跑到终态，
检查过才放行。推早了，玩家的"赛前后下注"变成"赛后下注"，整组条目作废；
推晚了只是慢，推早了是白跑。

## 阶段 3：FAIL 修复闭环（轮次制——攒批修，不是一条一修一发）

一条 FAIL 修一次、发一次服 = 每轮都重启 dev 打断别人、白等编译发布。闭环按**轮**推进：

```
一轮实跑收齐全部 FAIL（同一套环境同一套代码跑出来的才有可比性）
  ─► 批量分诊（盘点表：代码问题 / 环境问题）
  ─► 批量修改（每处带修改契约；环境问题则 GM 补数/回基线）
  ─► 一次代码复审（全部改动一起审，顺带互查改动间冲突）
  ─► 一次编译发服（红级决策，一轮只问一次）
  ─► 回基线重造环境 ─► 统一复跑全部 FAIL + 受影响条目 ─► 未清零进下一轮
```

**不收敛熔断**：连续两轮 FAIL 集合基本不变 = 大概率在改错方向、或断言本身有问题——
停下来向用户复盘（改了什么、为什么没效果、怀疑什么），不许闷头进第三轮烧时间。

**修改 agent 输出契约（治改码黑箱）**——改完必须交：

1. **改动清单**：每处 `file:line` + 改前/改后 + 为什么改 + 对应哪条 FAIL 条目 ID。
2. **最小化证明**：只改分诊定位到的点。**禁止顺手重构、顺手加防御、顺手改风格**——
   复审黑箱的根源就是修改 agent"一改改一片"，diff 越大复审越验不动。
3. **影响面自述**：改了哪些字段/状态？这些字段的所有消费方（推送、落盘、跨服转发）
   有没有被波及？修改 agent 自己先答一遍，复审 agent 拿它当靶子。

**复审 agent 的输入是三角，不是裸 diff**：diff + 「期望表现 vs 实测证据」 + 修改理由。
只给 diff 复审，它验不了"改的是不是对的问题"。复审重点四问：

- 改动是否真正命中 FAIL 根因（不是绕过断言/放宽校验让测试变绿）？
- 有没有破坏既有配对（扣费↔退款、发奖↔去重、改缓存↔落盘标记）？
- 改的状态字段有没有对应的推送覆盖（改了 A 推的却是只含 B 的推送）？
- 有没有违反消息契约（某分支从回包变成不回包 / 回了两条）？

- **代码复审**：走项目既定的复审入口，**修完必复审，
  复审不过不许发服**。
- **复跑**：先回基线重造环境，再复跑 FAIL 条目及其受影响条目（同状态机的相邻条目），
  全 PASS 才销账。**修完不复跑 = 没修。**
- 复审发现的共性问题（别的条目同模式）要回流清单：补条目、再验。

## 看板、证据落盘与断点续跑（治主 agent 上下文爆炸与跨会话丢失）

**清单文件即实时看板**：

- 状态列随实跑实时更新（PENDING / PASS / FAIL / ⚠️环境阻 / 需客户端确认），
  证据路径写进对应行——清单从"开工前的计划"变成"随时可查的进度事实"。
- **条目 ID 一旦分派即冻结**：跨会话、跨报告、跨 agent 引用都以 ID 为准；
  中途重排/改号 = 全部引用作废。

**证据落盘，不进上下文**：

- 三路证据（回包原文、GM see 输出、日志切片）按条目 ID 落盘到
  `.tmpfiles/<功能>验收/证据/`。
- 子 agent 交付 = 结构化结论一行：`条目ID | 状态 | 一句话结论 | 证据文件路径`，
  原始输出不带回对话。
- 主 agent 只持有看板摘要与任务表，需要裁决冲突/复核某条 FAIL 时再按路径取证据——
  主 agent 的上下文要烧在统筹上，不是当证据中转站。证据全灌进主对话，
  跑到一半上下文被压缩，等于验收现场失忆。

**断点续跑**：长验收跨天、会话中断、上下文压缩都是常态。恢复时读看板：
已 PASS 不重跑，FAIL 走闭环，⚠️环境阻 检查环境是否已补齐。
跨天开工先重读需求文档（活文档，策划可能中途改了口径）再续跑。

**长跑监控纪律（防"幽灵监控"）**：

- 会话退出/回合结束 = 所有后台监控与后台任务**当场终止**——没有任何东西会在你离开后继续盯。
- 宣称"后台监控中"前，必须真实存在已武装的 Monitor / 后台任务，并在汇报里给出任务标识；
  没有就不许说——那是向用户承诺一个不存在的哨兵，用户以为有人守着，实际现场空无一人。
- 长跑（批量战斗推进、定时结算、跨服聚合）只有两种合法做法：① **本回合等完**——
  后台命令跑着、本回合阻塞等终态再汇报结果；② 等不完就**明说**"会话退出监控即停，
  下次进来我重查状态继续"。不许默默结束回合然后假装有人盯着。
- 会话恢复后第一件事是重查服务端真实状态（GM see / 日志），确认长跑实际推进到哪一轮，
  **不按记忆里的进度继续推**——中断期间可能被重启、被重置、被别人动过。

## 打断控制：决策分级（治频繁打断用户）

开工前与用户约定三级决策，默认按此执行，不再逐条问：

| 级别 | 事项 | 处理 |
|---|---|---|
| **绿（自主执行）** | GM 造数/重置、发消息探针、复跑、回基线重造环境、按文档字面解读新歧义（记录待确认） | 直接做，动作记入日志 |
| **黄（攒批问）** | 新需求歧义影响 ≥3 条条目语义、改动落在共享文件、清单外发现疑似 bug | 记入待确认项继续跑，阶段汇报时**批量**问 |
| **红（立即问）** | 发布/重启会影响他人使用的服务器、删不可再造的数据、改动超出本功能范围 | 当场停下来问 |

原则：**问题不阻塞主流程**。子 agent 遇到疑问一律"按字面执行 + 标注待确认 + 继续跑"，
把打断留给红级事项；黄的攒着，一轮跑完一次性摆出来——用户答一批的成本远低于答十次单点。

## 阶段 4：全员终态后合并报告（主 agent 纪律）

- **记录每个子 agent 的任务 ID 与状态**，全程跟踪；启动成功 ≠ 完成。
- **全部子 agent 进入终态（完成/失败/取消）且成功结果全部到手之前**：
  不总结、不出最终报告、不说"都跑完了"。收到部分结果就先处理能独立推进的事，等齐剩下的。
- 提前终止（用户叫停等）：显式取消仍在运行的子 agent，等取消确认，
  这些按"已取消"入报告，**不许伪装成已完成**。
- 合并时：去重、核对冲突（两个 agent 对同一条目结论相反 = 重新实测裁决）、
  每条 FAIL 附完整"分诊→修复→复审→复跑"链条。
- 有子 agent 失败/取消的，最终报告必须说明其对覆盖率的影响。
- 报告本体仍走 Step 7 模板 + `verify_report.py` 闸门；覆盖率声明里写清
  哪些条目是哪个 agent 验的。

## 反模式（见了就纠）

| 反模式 | 纠正 |
|---|---|
| 不列清单直接跑，测完只有主流程 | 回阶段 0，以消息清单为纲补齐 |
| 清单条目没写期望表现就分派 | 打回，先从需求文档抄预期 |
| agent 拿到条目后自己脑补"应该是对的" | 期望表现只准来自文档与断言表 |
| FAIL 了直接改码，不看盘点表 | 先分诊：漏实现 ≠ 环境问题 |
| 修完代码不复跑就销账 | 修完不复跑 = 没修 |
| 修完不复审就发服 | 复审是发服前置闸门 |
| 主 agent 亲自下场跑条目 | 主 agent 只统筹，实测下放 |
| 部分结果就出总结报告 | 等全员终态，纪律见阶段 4 |
| 一个 agent 跑所有身份 | 身份隔离，数据不互踩，交互靠并发 |
| 改码顺手重构/加防御，diff 一大片 | 最小化证明，只改分诊定位的点 |
| 复审只看裸 diff | 输入三角：diff + 期望vs实测 + 修改理由 |
| 复跑沿用上一轮的脏环境 | 回基线重造环境再复跑 |
| 每遇到歧义就停下来问用户 | 按字面执行+标注，黄级攒批，红级才打断 |
| 清单没经用户确认就分派 | 评审闸门：期望表现列先过目一次 |
| 一条 FAIL 修一次发一次服 | 轮次制：攒批修、一次复审、一次发服 |
| 连续两轮 FAIL 不收敛还闷头跑 | 熔断：停下来向用户复盘方向 |
| 原始回包/日志全灌进主 agent 上下文 | 证据按条目 ID 落盘，只回结论+路径 |
| 会话断了从头重跑全部条目 | 清单即看板，断点续跑，PASS 不重跑 |
| 玩家 agent 发全局 GM 指令 | 全局操作只归驱动 agent，玩家只动自己对象 |
| 接到模糊指令直接开跑 | 主 agent 先复述意图+分派方案，确认后再执行 |
| 宣称"后台监控中"但无真实监控任务 | 只有真实武装的监控才许报，汇报附任务标识 |
| 长跑靠"会话退出后自动继续" | 会话退出监控即死；本回合等完，或明说停止、重开先重查状态 |
