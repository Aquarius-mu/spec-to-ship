# 设计依据与自我辩证

> **每条规则必须能指到一条真实事故，否则不写。** 规则的数量要少于痛点的数量，
> 否则规则本身就成了新的痛点。

---

## 一、证据基础

- 数据源：多套本地会话归档。
- 时间跨度：约 5 个月。
- 局限：只覆盖本机归档；早期记录可能缺失。

## 二、真实失效模式（按频次）

| 模式 | 命中 | 典型抱怨 |
|---|---|---|
| **重复犯错** | 180 | "说过好几次了还是不对"、"反反复复出错" |
| **做错 / 跑偏** | 145 | "理解错了"、"你不要解决其他问题" |
| **没做 / 只做一半** | 113 | "这个需求没有做"、"脚本没改吗" |
| **慢 / 臃肿** | 131 | "策划只有两分钟耐心"、"skill 越来越臃肿" |
| 提案子 / 需求 | 431 | 需求多数来自文档 + 即时口述 |
| 要求实跑验证 | 108 | "自己跑一下"、"复现" |
| 提 subagent | 23 | 有要求用，也有明令不用 |

> 而"待确认"里有相当一部分其实历史会话里已经答过。

## 四、规则集（每条可溯源）

### 强制三条（30 秒）

| # | 规则 | 治什么 |
|---|---|---|
| M1 需求出处 | 动手前写清"来自文档§x / 用户原话 / 台账 D-xx" | 做错/跑偏 |
| M2 完成定义 | 文件 + 需求条目 + 验证方式，三者缺一不算完 | 没做/只做一半 |
| M3 先例差异表 | 先例有/本案有/本案独有，标"禁止照搬" | 抄错 |

### 按需

| 触发 | 动作 |
|---|---|
| 文档案子 + 需求 > 20 条 | 派提取 agent 出 R-xx |
| 改字段/协议/枚举/配置键 | 改动传播检查 |
| 多人协作 | 改动白名单 |
| 有文档 | 完成后回写 |
| 有靶场 | 必须实跑 |

### 明确不做

不强制多 agent；不强制评分；不给小需求写规格；不新增未验证的脚本。

## 五、错误模式台账（P-xx）

只收跨功能重复出现的模式；一次性问题记需求台账。

| ID | 模式 | 自检 |
|---|---|---|
| P-01 | 抄先例抄来先例独有的东西 | 差异表填了吗 |
| P-02 | 漏掉先例的挂接点（登录/结算/清理/序列化） | 挂接点枚举完了吗 |
| P-03 | 改字段/协议只改一侧 | 全仓读写点列全了吗 |
| P-04 | 只改主流程，异常/离线分支没改 | 失败路径也改了吗 |
| P-05 | 说"做完了"，实际没改文档/脚本/配置 | 完成定义三件套齐了吗 |
| P-06 | 借用别的玩法专属错误码 | 是本玩法号段吗 |
| P-07 | 需求没写就自己补规则 | 这条规则的出处在哪 |
| P-08 | 用户答过的问题又问一遍 | 七路检索跑了吗 |
| P-09 | 过度防御代码模糊了不变量 | 运行时真会触发吗 |
| P-10 | 修完 bug 不检查同构位置 | 同类搜索做了吗 |

## 六、维护规则（防臃肿）

1. **先说依据**：新规则必须能指到一条真实事故，否则不写。
2. **先删后加**：每加一条规则，通读相关小节，删掉因它变冗余的旧句；总行数基本不涨。
3. **新坑进台账**：抽象成 P-xx，不往正文塞案例细节。
4. **体量预算**：`SKILL.md` 不超过 1150 行；`references/` 文件数不增加，新增内容优先并入既有文件。
5. **项目内容进适配层**：IP、路径、账号、专有命令只写 `adapter-*.md` / `project-anchors.md`，正文保持通用。
6. **季度复盘**：不再发生的规则降级或删除；用户说"太慢/太臃肿"时，先砍规则再加功能。
