# 自主取证：能自己找到的，绝不问人

> 真实原话："复审中挖出的 4 个待策划确认，这个你自己翻需求文档和配置表格啊，你不要问我啊，
> 很多方案答案里面都有！！！实在是需求文档和配置获取不了的话再说。"
>
> 提问不是沟通，是**把自己的检索工作转嫁给用户**。用户的时间比 AI 贵。

---

## 一、提问资格闸门（硬规则）

任何问题在问出口之前，必须依次跑完 **七路检索**。**七路全空才允许问**，否则提问作废。

| 路 | 找什么 | 怎么找 |
|---|---|---|
| **R1 正文** | 章节、段落、列表、删除线、图注 | `lark-cli docs +fetch --doc <token> --as user`，全文反转义后按关键词定位 |
| **R2 画板** | 流程图、状态图、界面示意、泳道图 | 文档里每个 `<whiteboard token=...>` 都要导出；**图上有、正文没有的同样是需求** |
| **R3 内嵌表 / Base** | 档位、概率、奖励、数值 | 文档里的 `<sheet token=... sheet-id=...>`、`<cite doc-id=...>` 逐个读；不许写"详见原表" |
| **R4 关联文档** | 被引用/继承的前置案子 | `<cite>` 链、版本历史里提到的文档、"同 XX 功能"指向的原文 |
| **R5 配置表** | 字段、默认值、单位、空值语义 | 策划 .xls、server.xml 映射、GM 公共参数、运营后台配置 |
| **R6 历史与台账** | 用户/策划此前答过的同一问题 | `.tmpfiles/<功能>/已决台账.md` + `scripts/history_search.py "<关键词>"`（搜本地全部会话） |
| **R7 代码与先例** | 现有实现、同类玩法怎么做的 | 全仓 grep、参照实现的同类逻辑、配置消费点 |

### 判定标准

| 检索结果 | 怎么办 |
|---|---|
| 找到**直接答案** | 用，标注出处（§x / 表X列Y / file:line） |
| 找到**可推导答案**（配置 + 规则能算出来） | 自己推，写出推导过程，不许问 |
| 找到**两个来源冲突** | **这种才允许问**，但必须带两边原文 + 你的倾向 |
| 七路全空 | 允许问，附"已查清单" |
| 只查到一半（缺一个数值） | 先把能定的定下来，只问缺的那一个，不要整条抛回给用户 |

## 二、什么该问、什么不该问

### 绝对不许问（用户明确表达过厌烦）

| 类型 | 例子 | 应该去哪找 |
|---|---|---|
| 案子写了的规则 | "退赛功能做不做？" | R1 正文 |
| 配置表里有的值 | "赠礼上限多少？" | R5 配置 |
| 现有代码怎么实现的 | "这个字段客户端要不要？" | R7 代码 + R3 表 |
| 之前答过的问题 | "离线补不补？" | R6 台账 |
| 有合理默认值的设计细节 | "失败回什么错误码？" | 项目既有规范 + 同类玩法 |
| 你自己没读全就抛出来的"待确认" | "这里需求不明确" | 先把 R1–R4 读完 |

### 该问（但一次问清）

- 产品取舍：两套方案都成立，且影响玩家体验/收费；
- 跨部门协调：需要策划改表、客户端改渲染、运维改配置；
- **不可逆操作**：删数据、发服、重启公共环境；
- **真冲突**：两个权威源给出相反答案；
- **成本极高**：两种做法工期差一个量级。

### 黄区：先做，再让用户否决

有合理默认值、且可低成本回滚的，**不要问**。做法：

```
假设：每日次数按自然日 0 点重置（依据：同活动其他限次一致）
如不对，告诉我，我改。
```

**先做 + 标注假设 + 允许推翻**，比"停下来等回答"快得多。用户要的是结果，不是问卷。

## 三、提问格式（不符合格式的提问直接作废）

```
Q-01 [阻塞:是/否]
问题：<一句话，可回答>
已查：
  R1 正文：§4.2.4「原文……」→ 未说明重置锚点
  R2 画板：token ZQ3k…，节点文字「每日 0 点刷新」→ 与正文不一致
  R3 内嵌表：sheet pNbm…，无该字段
  R4 关联文档：二期文档 §3.1「按自然日」
  R5 配置：t_activity 无对应列
  R6 台账：D-07 曾答"跟二期一致"
  R7 代码：RoleXxx.cpp:120 用自然日
冲突点：二期/画板/代码都说自然日，正文未写
我的倾向：自然日（3 个来源一致）
影响：影响 R-13 的验收断言
```

要点：
- **一次列全**，不要边做边问；
- **不阻塞主流程的问题攒起来批量问**；
- `[阻塞:否]` 的问题可以在收工时一起给，不要打断当前工作。

## 四、历史检索（治"之前明明答过"）

本地有完整会话归档时，先搜再问：

```bash
python scripts/history_search.py "退赛 补发 离线"
```

输出最近若干条你的原话与时间。**命中即视为已决**，写进台账，不许再问。

没有归档或搜不到，才进入 R5/R7。

**引用命中时先读上下文**：列表式回答里的「1 的话是 X，5 的话是 Y」，1/5 是**问题编号**，不是答案所指。
只抓关键词就归因，会把无关结论安到当前问题上——这类误引用比没搜到更危险，因为它看起来"有出处"。

## 五、自检（问出口前 10 秒）

- [ ] 七路都跑了吗？每路的**具体结果**能写出来吗？
- [ ] 这个问题，案子里真的没有吗？还是我没读到那一节/那个画板？
- [ ] 配置表里真的没有吗？还是我没找对表/列？
- [ ] 用户以前答过吗？搜过了吗？
- [ ] 它有合理默认值吗？有的话是不是应该先做再说？
- [ ] 我是不是把"读起来费劲"包装成了"需求不明确"？

> 六问有一项答不上来，就回去继续查。

## 六、反面证据（真实事故）

| 事故 | 用户原话 |
|---|---|
| 4 个"待策划确认"其实案子里都有 | "自己去翻需求文档和配置表，不要问我" |
| 反复确认已有结论 | "说过好几次了还是不对" |
| 把实现细节抛回用户 | "很多时候不该问我，应该自己从需求文档里挖" |
| 问完还不按答案做 | "这个问题之前问过了" |

**结论**：提问是最后手段，不是工作方式。
