# 自测断言表模板

> **断言表 = 需求的机器可读版。** 每条断言必须能回答"来源哪句需求、在哪个回包的哪个字段、期望什么"。
> 写不出这三个坐标的，说明需求还没读透，回去重读文档。

---

## 1. 怎么从需求文档抽出断言

对着需求文档逐条问三件事：

1. **玩家在哪个时刻看到什么？** —— 这是断言的语义（`desc`）。
2. **这个东西由哪条消息、哪个字段承载？** —— 去 IDL 里找（`cmd` + `field`）。
3. **期望值是什么？** —— 文档写死的直接抄；文档没写死的用关系式（`>=` / `len>=`），别自己编数。

抽不出字段的，说明**服务端可能根本没下发** —— 那本身就是一条待查的发现，记进报告的"需确认项"，不要为了凑断言硬编。

**来源列必填**（`source` 写文档名 + 章节号）。验收报告要能反查回需求，这一步省不得。

## 2. 文件格式（JSON）

```json
{
  "title": "<功能名> · GetInit 首屏",
  "source": "《<需求文档名>》2.1.2",
  "probe": "tmp_am_getinit",
  "uid": 100001,
  "zone": 1,
  "asserts": [
    {
      "id": "A1",
      "desc": "开启后返回淘汰赛分区ID",
      "source": "2.1.2",
      "cmd": "Cmd_<功能>_GetInit_SC",
      "field": "iDistrictId",
      "op": "==",
      "value": 1
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `title` / `source` | 报告标题 + 需求文档出处 |
| `probe` / `uid` / `zone` | 复现用（对应 `selftest.py run <probe> --uid --zone`） |
| `cmd` | **回包结构名**（`-- Response` 后面那串），不是请求名 |
| `field` | 字段路径，支持嵌套与下标：`stSchedule.iStateEndTime`、`vMember[0].iRoleId` |
| `op` | 见下表 |
| `value` | 期望值；`exists` 不用给 |

### 支持的操作符

| op | 含义 | 例 |
|---|---|---|
| `==` / `!=` | 相等 / 不等 | `"iState": 3` |
| `>` `>=` `<` `<=` | 数值比较 | `"iCurrentSeason": >=1` |
| `len==` `len>=` `len>` | 容器长度 | `"vMember": len==32` |
| `in` | 实际值 ∈ 期望数组 | `"iState": [3,4,5]` |
| `contains` | 期望值 ⊆ 实际（字符串/列表） | |
| `exists` | 字段存在即可（值任意） | |

## 3. 怎么跑

```bash
# ① 生成探针（字段名会自动带出来）
python selftest.py gen Cmd_<功能>_GetInit_CS --out tmp_<功能>_getinit

# ② 改探针里的值（需要入参的消息），然后跑并留存原始输出
python selftest.py run tmp_<功能>_getinit --uid 100001 --zone 1 \
  --save .tmpfiles/<功能>_getinit.out

# ③ 比对
python selftest.py check plan.json .tmpfiles/<功能>_getinit.out
# 退出码 0 = 全 PASS；非 0 = 有 FAIL/MISS
```

## 3.5 没有标准答案的断言怎么写（蜕变关系）

**战斗结果 / 匹配 / 排名 / 随机掉落 / 战力** 这类输出，文档和配置里都没有"正确值"。
**不要跳过它们，也不要凭感觉写"看起来合理"** —— 改写成**关系断言**（见 SKILL.md「蜕变关系」）。

| 关系 | 断言写法 | 落地形态 |
|---|---|---|
| **确定性** | 同输入跑两次，关键字段应相等 | 跑两次存两个输出，比对同一路径 |
| **单调性** | 输入↑则输出不应↓ | 造两组输入（强/弱），比 `>=` |
| **保序性** | 序关系应保持 | 检查列表相邻元素满足 `>=` |
| **双视角对称** ★ | A 的记录 ⟺ B 的记录 | 两个角色各发一次，交叉比对 |
| **守恒** | 进出配平 | 扣费前后余额差 = 配置消耗 |
| **幂等** | 重复 N 次 = 1 次 | 连发同一请求，比第 1 次与第 N 次状态 |

**双视角对称的落地**（最实用，且不需要知道谁该赢）：

```lua
-- 同一场战斗，攻守双方各取一次
local _, a = dogame(Cmd_GetFightReport_CS(fightId), uidAttacker)
local _, b = dogame(Cmd_GetFightReport_CS(fightId), uidDefender)
-- 断言：a 里的攻方 = b 里的攻方；a 的胜负与 b 的胜负应互为反面
```

写进 plan.json 时，关系断言同样用 `==` / `>=` 表达，只是**期望值来自另一次实测**而非文档。

## 4. 写断言的三条纪律

1. **一条断言只测一件事。** `iState==3 且 vMember 满` 要拆两条 —— 合并了就看不出是哪半坏了。
2. **FAIL 必须给证据，不许改断言。** 期望值与实测不符时，先确认期望值是不是抄错了；确认没抄错就是**真 bug**，进报告。为了让报告好看而把 `==` 改成 `>=` 是自欺。
3. **MISS 比 FAIL 更值得警惕。** 回包里根本没这条结构，往往意味着"这个分支压根没下发"，而不是"测试写错了"。

## 5. 断言覆盖度自查

跑完对照下面几条，缺哪条补哪条：

- [ ] **正常路径**：每个消息的成功回包，关键字段都断了吗？
- [ ] **空结果路径**：没有数据时回的包，断言的是"空"而不是"崩/不回"吗？
- [ ] **错误路径**：非法入参该回的错误码，断言了吗？（用探针故意传错值）
- [ ] **时机**：状态改变后的回包字段，与改变**同步**吗？（回包里的值 = 落库的值）
- [ ] **推送**：该有的主动推送收到了吗？（`vPush` 里有对应结构）
- [ ] **幂等/重复**：同一操作连做两次，第二次的反馈是什么？（断言 or 记进报告）
- [ ] **状态可查**：玩家侧看到的，与 GM 从服务端查出来的**一致**吗？（这需要三路取证，见 SKILL.md Step 6）
