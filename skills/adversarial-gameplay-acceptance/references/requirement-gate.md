# 需求锚定与规格模板（验收的第 -1 步）

> 本文件是模板库，**按需取用**，不是每次都必须走完的流程。
> 为什么这样分级：真实数据里"慢/臃肿"被抱怨 131 次，"没做"113 次——**流程过重本身就会制造问题**。
> 设计依据见 `design-rationale.md`。

---

## 一、先决定用哪一档

| 档 | 触发条件 | 要做什么 | 耗时 |
|---|---|---|---|
| **轻档** | 用户口述的小改动、hotfix | 只做 M1 需求出处 + M2 完成定义 | 30 秒 |
| **中档** | 有案子、需求 10~20 条 | M1 + 用 §四 分流缺口 + 玩家预演三问 | 10 分钟 |
| **重档** | 有案子、需求 > 20 条、多进程/跨服 | 全套：§六 派 agent + §八 对账矩阵 + §九 回流 | 1 小时+ |

**判据**：如果这个功能上线后玩家会花钱、会丢数据、会卡住，就至少中档；其余走轻档。
**禁止**：把轻档任务硬套重档流程——那是拿流程代替思考。

## 二、六维需求就绪度（参考维度，非打分闸门）

逐维看一眼，标 `达标 / 部分 / 缺失`。**明显缺失的维度**转入缺口清单，其余不阻塞。
不要为了凑一张全绿的评分表而拖延开工。

| # | 维度 | 合格判据 | 不达标长相 | 通常谁来补 |
|---|---|---|---|---|
| 1 | **可验证性** | 每条需求都能写出 `Given 前置 When 操作 Then 可观测结果` | "优化体验""合理展示""尽快处理" | 策划 |
| 2 | **反馈闭环** | 每个操作都写明：成功看到什么、失败看到什么、空结果看到什么 | 只写"支持 X"，没写点完屏幕上有什么 | 策划 + 客户端 |
| 3 | **生命周期** | 初始态 / 离线变更 / 重登回填 / 重启恢复 / 跨周期重置 / 并发重复 全部有定义 | 只描述"在线正常操作" | 策划（默认值）+ 开发（技术态） |
| 4 | **数据口径** | 单位、时区、0 与空的语义、去重维度、全量还是抽样，逐项写明 | "每天 3 次"但没说按自然日还是 24 小时 | 策划 |
| 5 | **边界与失败态** | 0 / 上限 / 上限±1 / 资源不足 / 资格不符 / 已结束 各自的反馈 | 只写正常路径，异常路径留给开发脑补 | 策划 + 开发 |
| 6 | **跨端跨进程** | 谁是权威、同步失败怎么办、多端并发以谁为准 | "跨服同步一下"但没说同步失败 | 开发 + 策划 |

**判定记录写法**（写在需求规格头部即可）：

```
就绪度: 生命周期△ 数据口径✗ 其余✓ → 缺口 Q-03…Q-05
```

> 真实分布：某功能验收提了约 69 条问题，其中 26 条是"只实现了正常在线操作"——**第 3 维是最高发的缺失**。

## 三、缺口清单（唯一提问入口）

每条缺口固定六段，缺一段不许问：

```
Q-07 [维度:数据口径] [阻塞:是/否]
问题: "每天 3 次"是按自然日 0 点重置，还是按上次操作后 24 小时？
已查七路:
  R1 正文：§3.2「每日可参与 3 次」→ 未写重置锚点
  R2 画板：token ZQ3k…，节点「每日 0 点刷新」→ 与正文不完全一致
  R3 内嵌表：sheet pNbm…，无该字段
  R4 关联文档：二期 §3.1「按自然日」
  R5 配置：t_activity 无对应列
  R6 历史：history_search "每日 次数" 命中 D-07「跟二期一致」
  R7 代码：RoleXxx.cpp:120 用自然日
冲突点: 正文未写，其余四个来源都说自然日
我的倾向: 自然日（依据 R2/R4/R6/R7）
影响: R-13 的验收断言、离线跨天场景
```

**七路没跑完，不许发问**（见 §四 与 `self-research.md`）。

---

## 四、缺口分流：七路检索

顺序固定：**正文 → 画板 → 内嵌表/Base → 关联文档 → 配置表 → 历史/台账 → 代码先例**。
七路全空才允许问；冲突时带两边原文。完整规则与提问格式见 `self-research.md`。

三条禁令：
- 用户答过的不许再问（先跑 `history_search.py`）；
- 先例只能作建议，不能替代正文/画板/内嵌表；
- 只查到一半的，只问缺的那一个数，不许整条抛回。

## 五、已决台账（防重复提问的地基）

文件：`.tmpfiles/<功能>/已决台账.md`

```
| ID | 问题 | 结论 | 来源 | 日期 | 适用范围 |
|----|------|------|------|------|----------|
| D-01 | 退赛功能做不做 | 不做 | 用户口头 | 2026-01-02 | 本功能 |
| D-02 | 离线是否补发 | 不补，只在领取时发 | 用户口头 | 2026-01-02 | 本功能 |
| D-03 | 次数为 0 的语义 | 0 = 不限次 | 配置表注释 | 2026-01-03 | 全局 |
```

规则：
- **一条决策一个 ID**，永不删除；推翻时新增 `D-xx` 并标 `取代 D-yy`。
- 台账是**跨会话**的：下一次验收先读台账，不重新问。
- 用户口头澄清的效力**高于**案子字面，但必须在台账标注日期与适用范围。

## 六、派 agent 契约（重档用，轻/中档可跳过）

> 用户对 subagent 的态度是**分场景的**：复杂案子要求"多开 agent 思考"，简单改动明令"尽量不要用"。
> 所以这里只给契约，不强制派。判据：案子章节多、有画板/内嵌表、需求 > 20 条 → 派；否则主 agent 直接读。

重档时至少三个独立产出，**不许互相看**（趋同就漏盲区）。

| agent | 输入 | 产出 | 禁止 |
|---|---|---|---|
| **提取**（团队专用 agent 或通用） | 需求文档全部载体 | `需求规格.md`：R-xx 条目 + 开发侧缺口清单 | 不许写实现方案；不许脑补文档没写的 |
| **质检** | 需求规格 + 六维表 | 就绪度评分 + 缺口清单 Q-xx | 不许替策划定规则 |
| **玩家预演** | 需求规格（只读需求，不看代码） | 按玩家旅程走一遍，标出"走到这里会卡住/会困惑" | 不许看实现反推需求 |

**合并规则**：三份清单去重后，按 §四 分流；冲突项单列，以案子原文为准，案子没写的进 Q 清单。

**产出路径**（固定，下游直接读）：

```
.tmpfiles/<功能>/
  需求规格.md      ← R-xx 条目 + 就绪度评分
  已决台账.md      ← D-xx
  缺口清单.md      ← Q-xx
  对账矩阵.md      ← 第八节
```

**派发提示词（可直接复制）**：

```
【提取】读需求文档：正文、内嵌表格/Base、全部画板、评论区、修订历史、空章节。
产出 .tmpfiles/<功能>/需求规格.md（R-xx 编号 + 出处），不做实现设计、不脑补文档没写的。

【质检】只读 需求规格.md，不读代码。逐维看一眼，把明显缺失的写 Q-xx：
问题 + 文档原文 + 已查七路 + 建议默认值 + 影响。
另以不了解实现的玩家身份走一遍旅程，标出"走到这里会卡住/困惑"。
产出 .tmpfiles/<功能>/缺口清单.md，不要改需求规格。
```

## 七、玩家预演 agent 的三问

按需求规格走一遍玩家旅程，每个节点问：

1. **玩家此刻看到什么？** 需求里写了吗？没写 = 缺口（第 2 维）。
2. **玩家如果做了意料之外的动作呢？** 连点、中途退出、断线、跨天、活动刚结束——需求里写了吗？没写 = 缺口（第 3/5 维）。
3. **玩家怎么知道成功了？** 需求里给了可观测结果吗？没给 = 缺口（第 1 维）。

> 这个 agent 只看需求、不看代码。它找的是"需求本身没考虑玩家"，不是"实现没写"。

## 八、三向对账矩阵（贯穿实现与验收）

每一行必须能走完：**需求 → 实现 → 验收证据**。

```
| RQ | 需求摘要 | 实现位置 file:line | 状态 | 验收证据 | 结论 |
|----|----------|--------------------|------|----------|------|
| R-01 | 每日 3 次 | RoleXxx.cpp:120 | 已实现 | out/r01.txt | PASS |
| R-02 | 失败给提示 | 未找到 | 未实现 | — | FAIL |
| (—) | 需求未写但代码有：自动补队 | RoleXxx.cpp:88 | 加戏 | out/a01.txt | 待确认 |
```

**双向都要对**：
- 需求 → 实现：找不到实现 = **漏实现**。
- 实现 → 需求：代码里有、需求没写 = **加戏**（同样要报，可能是风险，也可能是隐藏需求）。

**以玩家动作为轴，不以章节名或消息名为轴**：案子按界面章节写、代码按消息模块写，两边直接对会错位。
一个 RQ 可以对应多条消息，一条消息也可以覆盖多个 RQ。对不上的，先怀疑自己的映射，再怀疑实现。

**覆盖率只认矩阵，不认口头**：`已实现且 PASS / 总条目`。未实现、未验证、待外部输入分别单独计数，不许合并成"基本完成"。

## 九、反向回流：验收发现 → 需求

验收结束时，每条发现必须归入下列之一：

| 归类 | 判据 | 去向 |
|---|---|---|
| **实现漏了** | 案子写了，代码没做 | 修代码，回到原 RQ |
| **实现错了** | 案子写了，代码做反了 | 修代码，回到原 RQ |
| **需求没写** | 案子和台账都没有，但玩家会踩到 | **新增 RQ-new，进缺口清单，问策划** |
| **案子本身矛盾** | 正文/表格/画板互相冲突 | 原样列两边，等裁决 |

> 第三类最重要：**只修代码不补需求，下一轮还会在同一个地方踩。**
> 每轮验收结束，需求规格的条目数只应增加（新增 RQ-new），不应减少。

## 十、与相邻能力的边界（不重复造）

| 能力 | 负责 | 不负责 |
|---|---|---|
| `spec-to-ship` | 端到端编排与门禁 | 具体的提取/实现/验收方法 |
| 需求提取（团队专用 agent 或通用） | 文档 → 结构化需求 + 开发侧缺口 | 评分、验收 |
| 需求驱动开发（团队若有） | 需求 → 实现覆盖率 100% | 玩家反馈闭环、靶场实测 |
| **本 skill** | 需求锚定 → 实现 → **玩家看到什么**；反向质检需求 | 代码质量、规范 |
| 代码审查 | 代码质量与安全 | 业务反馈闭环 |

**顺序**：提取 → 本闸门 → 实现 → 本 skill Step 0–7 → 验收回流。
团队没有专用提取/开发 skill 时，本 skill 的 Step -1 可独立使用。

## 十一、开工检查单（按档勾选）

**轻档**（30 秒）
- [ ] M1：需求出处写出来了
- [ ] M2：完成时准备交出「文件 + 条目 + 验证方式」

**中档**（+10 分钟）
- [ ] 缺口已按 §四 分流，问人的一次性列出
- [ ] 已决台账扫过
- [ ] 玩家预演三问已答

**重档**（+1 小时）
- [ ] 需求规格存在，每条有 R-xx 与出处
- [ ] 关键缺失维已转成 Q-xx
- [ ] 三向对账矩阵已建（允许实现列为空）
- [ ] 环境指纹已记录（见 SKILL.md 开工第 0 步）

## 十二、改动传播检查（改字段/协议/枚举/配置键时必做）

> 真实高频：只改了定义侧，没改读取侧；只改了一个进程，另一个进程还在用旧值。

1. 列出被改符号：字段名 / CmdId / 枚举值 / 配置键。
2. 全仓搜索**所有**读写点（定义、序列化、加载、缓存、推送、日志、GM、客户端引用）。
3. 每个点标注 `已改 / 无需改+理由 / 待确认`。
4. 三个方向都要搜：**写 → 读**、**旧值 → 新值**、**本进程 → 其它进程**。

**完成判据**：搜索结果为 0 处未标注，才允许说"改完了"。

## 十三、错误模式台账（P-xx，跨功能复用）

> 与需求台账 D-xx 分开：D-xx 记"这个功能定了什么"，P-xx 记"AI 反复犯什么"。
> 完整清单与依据见 `design-rationale.md` §六。开工前扫一遍，只留与本轮相关的。

最小集合（必查）：

| ID | 自检 |
|---|---|
| P-01 | 抄先例前，差异表填了吗？ |
| P-02 | 先例的挂接点（登录/结算/清理/序列化）枚举完了吗？ |
| P-03 | 改字段/协议，全仓读写点列全了吗？ |
| P-04 | 失败/离线/异常分支也改了吗？ |
| P-05 | 代码之外的文档/脚本/配置改了吗？ |
| P-08 | 已决台账扫过了吗（不许重复问）？ |
| P-10 | 修完一个 bug，同构的其它地方搜了吗？ |
