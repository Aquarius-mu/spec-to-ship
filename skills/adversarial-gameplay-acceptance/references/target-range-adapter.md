# 靶场适配层规范（通用）

> SKILL.md Step 6「靶场实跑」的底层设施。**本文不含任何团队的具体地址、账号、命令**——
> 它定义的是"要接哪六样能力、每样长什么样"。
> 某团队的参考实现见 `adapter-<团队>.md`（如 `adapter-example.md`），可整份替换。

---

## 一、为什么要适配层

靶场差异不在"用什么语言写驱动"，而在**这六样能力有没有、怎么调**。
只要这六样齐，SKILL.md 的流程一字不改就能跑；缺哪样，就按降级矩阵退到那一档。

**换团队不要改 skill 本体，也不要去改别人的脚本硬套。** 照下面的契约写你自己的驱动。

---

## 二、六件套契约

每一样都定义成"**输入 → 输出**"的能力接口，不看实现方式（ssh 也好、HTTP 也好、本地进程也好）。

### ① 消息探针（必须有，否则退到"只能 GM 驱动 + 读码"）

| 项 | 契约 |
|---|---|
| 输入 | 一条 CS 消息（名字 + 字段值）、目标角色、目标实例 |
| 输出 | 该 CS 的 SC 应答 + 本次连接收到的**主动推送列表** |
| 附加能力 | 能发 GM 命令（与协议同一次连接最好，能看到上下文）；能造登录态 |

**关键要求**：必须能拿到**主动推送**。GM 和日志都看不到"玩家视角收到了什么推送"，
而这恰恰是反馈闭环验收里最容易出问题的一环（该推没推、推错人、重复推）。

### ② GM 通道

| 项 | 契约 |
|---|---|
| 输入 | GM 命令字符串、目标实例 |
| 输出 | 命令执行结果（**注意：回执 ≠ 生效**） |
| 附加能力 | 命令清单在哪（新增 GM 往哪加）；能否跨实例转发 |

**关键要求**：判定生效必须走**业务级证据**（状态查询、埋点日志、推送），不能信回执文本。
诊断类 GM 应当把信息放在正文里而不是只回错误码——否则拿不到内容。

### ③ 日志

| 项 | 契约 |
|---|---|
| 输入 | 实例号、服务类型、日志 kind、行数/过滤条件 |
| 输出 | 日志切片 |
| 附加能力 | 实例 → 所在机器的定位方法 |

**关键要求**：区分 kind 的优先级——**告警类日志优先级最高**，状态机不推进、结算失败基本都在那。
日志常常不在编译机上，要能跨机取。

### ④ 数据（数据库 / 缓存）

| 项 | 契约 |
|---|---|
| 输入 | 查询语句 |
| 输出 | 结果集 |
| 附加能力 | 改前留快照的能力（回滚 / 重造） |

**关键要求**：**分清权威态与镜像态**。多实例系统里，你连的这台可能只是镜像，
查出来的值不是真相。查错地方会得出**完全相反**的结论。

### ⑤ 编译与发布（含修复闭环契约）

| 项 | 契约 |
|---|---|
| 输入 | 代码根目录、编译命令、发布命令（含目标实例参数）、单实例/多实例的区别 |
| 输出 | 新二进制上线（**记进环境指纹**） |
| 附加能力 | 启动校验（起不来要告警）、增量发布（只发改动的服务） |

**落进 `project-anchors.md` 的六件事**（少一件闭环就跑不动）：

| # | 要写清 | 缺了会怎样 |
|---|---|---|
| 1 | **代码根目录**（哪个盘/哪台机的哪份副本；本地与远端是否同一份） | 改了不生效，或改错副本 |
| 2 | **编译命令** + 耗时 + 产物落在哪 | 不知道测的是不是新代码 |
| 3 | **发布命令** + 目标实例怎么传 | 发错机器 |
| 4 | **只发哪几个进程**（改了 GameServer 就别全发） | 白等半小时 |
| 5 | **启动校验**（起不来谁告警、去哪看） | 环境挂了还以为在测 |
| 6 | **落地判据**：怎么确认目标实例真的换了新二进制 | 拿旧二进制测，结论全废 |

**闭环要求**（对应 SKILL.md「修复闭环」）：

- 定位 → 改码 → 编译 → 发布 → 重测，**每一环都要有独立判据**，不能拿上一环的返回值当证据。
- 编译判据：产物 mtime/hash 变化、日志出现构建成功行。
- 发布判据：**目标实例 PID 变了 / 启动日志时间戳更新**。
  **踩过：同一条发服命令连跑两次，只有第二次真的重启了目标实例**——返回成功不等于重启了。
- 多进程功能：**每个进程单独确认**（区服重启了不代表跨服重启了，跨服要认专属那行输出）。
- **默认只预演**，必须显式加确认参数才真跑；**发布影响半径最大，首次必须问用户**。
- 重测只跑 FAIL + 受影响条目，不重跑全量；连续两轮 FAIL 不变 = 熔断。

### ⑥ 需求源

| 项 | 契约 |
|---|---|
| 输入 | 文档标识 |
| 输出 | 最新版全文（结构化） |
| 附加能力 | 能读修订历史 / 评论（方案可能改过） |

**关键要求**：活文档，验收当天重读。会话里的旧摘录一律不信。

## 三、接入检查表（第一次接一个团队时过一遍）

```
□ 六件套各自"有 / 没有 / 降级为什么"，逐项填进 project-anchors.md
□ 每件写清：入口（命令 / URL / 路径）、参数、典型输出、已知坑
□ 生成一份 selftest.config.json（若用参考脚本）
□ 跑一次 selftest.py env（或你的等价体检命令），确认六件套都通
□ 拿一个已知功能做一次端到端演练：造状态 → 发协议 → 三路取证 → 比对
□ 把演练中踩的坑写回 project-anchors.md
```

接入完成的标志：**换一个从没接触过这个项目的人，照 `project-anchors.md` 能独立跑完一次验收。**

## 四、跨进程 / 多实例取证（通用五条）

> 凡功能横跨两个及以上进程/实例（区服 + 跨服、客户端网关 + 逻辑服、主 + 备），
> 下面五条通用，**不限于某个玩法**。它们只回答"**怎么读才是真值**"。

### 4.1 近端回包 ≠ 远端真相

前端/入口侧的回包常常取的是**本机镜像快照**（权威侧推送 + 秒级回拉），天然滞后。
「协议回 0」只说明**入口这一段跑到了**，不代表远端状态对。

⇒ 三路取证：① 玩家协议回包 ② 远端权威侧全量查询 ③ 远端日志。
**任两路打架 = 还有没查出来的问题**，别拿近端回包给远端状态背书。

### 4.2 要真跑，先把角色"加载"进内存

对战/结算类功能回拉数据走的是"从内存里找角色"——**角色不在内存就直接返回 NoUser**。
"EvenDeleted"这类命名只覆盖"已删除但仍在内存"，**不覆盖"从没加载过"**。
角色离线且未被加载 ⇒ 每场都缺数据重试，日志满屏缺阵，一场都不结算。

⇒ 推阶段前，先对每个参赛号发一次任意协议把它拉进内存。
⚠️ 自己发的设置类协议返回 0 **只代表本进程存好了**，远端要拿到还得靠这次回拉 ——
「协议回 0」≠「远端有数据」。

> 这是**数据态**问题最典型的形态。现象是"一直在重试""一场都没结算"，
> 第一反应不该是"代码坏了"，而是"数据态对不对"。

### 4.3 「真跑了」和「兜底跑了」长得一样

调度器重试耗尽会走**兜底结算**，**照样出结果、照样推进阶段** ——
只看进度/积分必然误判成"在跑"。

⇒ 判据只有**业务产物**（战报、流水、落库记录）：真跑有产物，兜底没有。
辅助看日志里对应错误计数是否停涨。

### 4.4 多实例调度：认"权威台"，不认本机

多实例共同承载一个逻辑单元时，只有**权威台**在驱动，其余是镜像。

- **先找号令台**：代码里通常有"取负责实例"的函数（自带存活过滤），查状态先查它。
- **判主规则必须唯一**：踩过"归属按 A 规则选一台、任期又按 B 规则选一台"⇒
  两台**同时让位**，谁也上不去，**且不自愈，只能重启或跑 GM**。
  心跳里播的任期必须**随对端存活一起过期**，只增不减必死锁。
- **诊断口径**：权威台的诊断输出看「负责台 + 对端在岗任期」；
  若「负责台=本机」而对端在岗任期更高，就是被任期判据挡住了。

### 4.5 推阶段：窗口起点和宽度都不恒定

用"回拨时间"推阶段的 GM，回拨量按天跳变，且**各阶段窗口不一样**：

| 阶段类型 | 起点 | 宽度 |
|---|---|---|
| 战斗类阶段 | 当天固定时刻起 | 多数 24h |
| 非战斗类阶段 | 当天 00:00 起 | —— |
| 收尾类阶段 | 当天固定时刻起 | **可能只有 2h** |

⇒ 回拨公式只保证"今天是第 N 天"，**不保证"已过当天开战时刻"**。
落窗口外的表现是**调度器一声不吭**（直接 return，不报错、不告警），最容易被误判成功能坏了。
**症状对照**：同一份数据只改回拨量，发起场次从 0 变成几十场。

> 这条也是**爆炸半径**的常见触发点：为了推进一个长窗口去重启公共实例，
> 往往不如"缩短窗口 / 用独占实例 / 直接改状态"半径小。

## 五、通用卡点分类（现象 → 先查哪一类）

| 现象 | 先查哪一类 |
|---|---|
| 探针里协议变量是空 / nil | ① 消息探针——协议定义更新了吗 |
| 连不上服务 / 拿不到代理 | ① 实例号写错，或该实例没起 |
| GM 返回"命令不存在" | ② GM 通道——命令名拼错 |
| GM 返回"对象为空" | ② 可能是"命令对但目标没数据"，≠ 真的角色为空 |
| 回包全 0 / 全空 | 入口通了说明进程在跑；看是不是上游没下发数据，走告警日志 |
| 改了代码没变化 | ⑤ 没编译 / 没发服 / 发错实例；核对**二进制部署时间 vs 提交时间** |
| 日志文件不存在 | ③ 实例定位错，或该 kind 当天没产生 |
| 满屏缺阵 / 一场都没结算 | 数据态——角色没加载进内存（见 4.2） |
| 有进度但查不到业务产物 | 很可能是**兜底**（见 4.3） |
| 读出来的是**旧值** | 查的是镜像，不是权威台（见 4.1、4.4） |
| 数值字段读出空 / 0 | 该字段类型是窄整型/字节，被当原始字节打印——换按字节解析 |
| 时间推阶段推不动、调度器一声不吭 | 落在阶段窗口外（见 4.5） |
| 多台都不干活、状态机永久停摆 | 排查"多台同时让位"（见 4.4） |

> 这张表的用法：**先分类，再深挖**。大部分"看起来像功能 bug"的现象，
> 在分类阶段就被证明是环境 / 数据 / 工具问题。**先过「假 bug 四问」，再断言代码 bug。**

## 六、落地判据：动作 ≠ 生效

**命令返回成功只证明"参数解析通过"，不证明"事情发生了"。**
造环境的每一步都要有一个**独立于该动作返回值**的判据，否则后面所有取证都建在沙子上。

接入时必须为六件套各自定出"怎么算真的生效了"，并写进 `project-anchors.md`：

| 能力 | 判据不能是 | 判据应该是 |
|---|---|---|
| ⑤ 编译 / 发布 | 命令返回 0 | 目标进程 **PID 变了**、启动日志时间戳更新 |
| ② GM 改状态 / 改时间 | 回执 "OK" | **回读那份状态**；改时间的要**等一帧**再读（有的实现只改基准不重算） |
| ② GM 塞数据 / 改配置 | 回执 "set OK" | **回读条数与字段值** |
| ① 发设置类协议 | 协议回 0 | **对端真的收到了**（对端日志 / 对端查询） |
| ④ 改库 / 改缓存 | SQL 执行成功 | **回查一遍**；注意落库可能是异步的，要等几秒 |

**通用失败模式**（都是"命令成功了但事情没发生"）：

- **命令返回成功，目标根本没动** —— 例如同一条发布命令连跑两次只有一次真的重启了目标
  （输出里那一段压根没出现）。**每次都要核对"目标真的重启了"的证据**，而不是命令的退出码。
- **动作只作用于指定的那一个对象**，不是"这一类对象" —— 多实例 / 多分片下要**逐个执行**，
  只做一次会让各份状态分叉。执行前先问：这个动作的作用域是"一个"还是"全部"？
- **改时间只改基准、不重算状态** —— 推进后立刻读会读到"旧状态配新基准"，
  据此判断推进结果必然误判。**等一帧再读。**
- **异步落库 / 异步回拉还没到** —— 立刻回查会以为失败。**先确认真实延迟量级，再定"等多久"。**

> 记账方式：把"动作 → 判据"列成表放进 `project-anchors.md`，
> 每次造环境照着核对，而不是凭记忆觉得"应该好了"。

## 七、模拟玩家的保真度：三档，别混

**"模拟玩家"不是一种做法，是一个阶梯。** 用哪一档决定结论能覆盖到哪：

| 档 | 怎么操作 | 保真度 | 能验到什么 |
|---|---|---|---|
| **高** | **只用客户端协议**，从登录开始按真实顺序走 | 最接近真实玩家 | 反馈路径、消息契约、客户端拿到的数据 |
| **中** | GM 造好环境 → **用协议做操作** | 中 | 操作路径真实，前置状态是造的 |
| **低** | GM 直接改状态 / 触发 | 低 | 只验服务端状态机，**验不了玩家反馈** |

**铁律：想回答"玩家会不会踩坑"，就必须用高档。**
低档跑得再顺，也答不了"玩家看到什么"——它压根没有玩家这一端。

**各档要标清楚**：报告里每条结论注明用的是哪一档，
`[纯协议]` / `[GM造环境+协议]` / `[GM直接驱动]`。

**提高保真度的具体做法**：

- **按玩家的顺序走**，不按代码结构走：登录 → 进界面 → 操作 → 收反馈，一条链走完
- **只用玩家能用的手段**：能用协议就别用 GM；GM 只用来**造前置**，不用来**代替操作**
- **带上玩家的随机性**：乱点、连点、在不对的时机操作、操作到一半退出、断线重连
- **从玩家的入口进**：走客户端会走的那条消息，而不是直接调内部函数

> 与「加速记账」互为镜像：**加速是往下走（省时间，但跳过路径），保真是往上走（费时间，但覆盖真实路径）**。
> 每次选择都要知道自己在哪一档、跳过了什么、结论因此弱在哪。
