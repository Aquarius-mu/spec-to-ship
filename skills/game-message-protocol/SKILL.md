# 消息协议（IDL）开发指南

> 本文只讲**消息层**：怎么定义、怎么接线、怎么避坑，不含业务逻辑。
> 文中类名/文件名是示例，动手前用 Grep 核实当前仓库的真实形态。

---

## 零点五、新消息设计六问

定义任何 CS/SC/Push/Status 字段前，按顺序问；前一问答"是"就停：

1. **能不能不开新消息？**
   - 查询类挂已有 Status；
   - 同界面多查询合一（用 `iType` 区分）；
   - 对偶操作合一（`iOper` / bool 区分）；
   - 整条消息能由"配置表 + 已有推送 + Status"拼出 → 删。

2. **Status 能不能用子结构？**
   十几个散字段平铺 → 合并成 2 个子结构 + 1 个 map。

3. **多值语义是不是写成了单值？**
   可同时存在多个（如多个增益同时生效）→ `map<id, 到期时间>`，不是 `id + 单一时长`。

4. **是不是查表就能得到？**
   等级上限/经验上限/消耗/返利/效果值/时长/名称/人数上限 → 客户端读表，不下发。

5. **是不是能推导？**
   状态标记、进度档位、是否已领、名次、回显参数 → 客户端自己算。
   **列表元素上已带的状态，不再单独下发聚合值**（每条都有 `bClaimed`，未领数让客户端数）。

6. **是不是该放查询消息而不是 Status？**
   见下方"Status 的边界"。

> **字段是精贵资源：写不出"客户端为什么非它不可"的字段，就是该删的字段。**

### Status 的边界

Status 会被功能状态变化频繁重推，**只放本进程内存里零成本能读到的状态**。

需要跨进程取、需要遍历名册排序、需要排行榜聚合的字段（人数、排名、多轮战果、计数、阶段）
**一律移到查询消息**——否则每次推 Status 都在触发异步，把入口状态包拖垮。

判据：**这个字段在本进程内存里能零成本拿到吗？** 拿不到就走 CS。

- 移出不是丢消息：用查询消息的 `iType=0 总览` 承载，页面进入时拉一次，配合已有 Push 更新在线状态。
- 回显参数可以删（客户端知道自己发了什么），**但分页的 `iOffset` 保留**——回包乱序时要用它把数据贴回正确的页。

### 配套硬规则

- **注释只说干嘛的，一句话。** 字段注释写语义边界（0 表示什么、仅哪个 type 填、查表可得）；CmdId 行只写"查什么/干什么"+ 参数枚举，不写设计理由、不堆长句。
- **IDL 没有前向引用**：被引用 struct 必须定义在使用者之前。
- **删字段必须同步改 C++**：`stSend.iXxx = stReq.iXxx` 指向已删字段直接编译错；全库 grep 字段名。
- **已落盘的结构，tag 号与类型都不能改。** 旧存档按旧类型写值，新结构解析直接抛异常；若"存档损坏就不建空对象"，整个对象永久打不开。
  - 正确做法：**要换结构就新开 tag**，旧字段保留并标 `[迁移兼容]`；新 tag 搬完旧数据后清零；`restore` 成功后调一次迁移函数，下次落盘自然收敛。
  - 判据：改任何 IDL 结构前先问 **"这个结构有没有已经写进持久化存储？"** 有就必须走兼容路线。
- **改已有 IDL 用脚本按锚点替换，替换后逐行核对相邻块**，避免插入新字段时吃掉相邻字段的注释。
- **未外放的消息删除后号段立即压实**，别留空号。
- **配置枚举必须对着表全量核对**，不能看前几行推断分组。正确做法：全表导出该列 → 去重 → 逐值对照名称建枚举。

## 一、五类消息，各走各的通道

| 类型 | 命名 | 定义处 | 注册处 | 触发/发送 |
|---|---|---|---|---|
| 客户端请求/响应 | `Cmd_Xxx_CS` / `Cmd_Xxx_SC` | `proto/client/ProtoBizXxx.idl` | `REGISTER_COMMAND(Xxx, flag)` | 客户端发 CS，`handle_Xxx` 里 `sendResponse(stSC)` 回 SC。**flag：同步 handler 填 5，异步 handler（回调里才回 SC）填 4** |
| 主动下推 | `Cmd_Push_Xxx` | 同上 | `REGISTER_PUSH(type, time, storenum, Push_Xxx)` | `CommandDispatcher::getInstance()->sendPush(zoneId, uid, stPush)` |
| 跨服转发 | `Forward_Xxx_Req` / `_Rsp` | `proto/inter/forward.idl` | `REGISTER_FORWARD(Xxx_Req)` / `REGISTER_FORWARD_RESP(Xxx_Rsp)` | `FORWARD_MGR->sendAsync("", 目标zone, 目标uid, 本zone, 本uid, stReq, cb)`；收端 `handleForward_Xxx_Req` |
| 公会/联盟命令 | `GuildCmd_Xxx_Req` / `_Rsp` | `proto/inter/guild.idl` | 见下方"注册对称规则" | `GUILD_MGR->sendCmdToGuild(...)` |
| 存盘/共享存储 | `CacheXxx` | `src/datastructs/*.idl` | 无需注册 | `idlToString` / `idlFromString` 序列化 |

### 公会/联盟命令的注册对称规则

公会服（GuildServer）通常**没有主动推送**：`Rsp` 只会是自己所发 `Req` 的应答。

**发送方式决定应答是否必须注册**——这是判定的唯一标准：

| 发送方式 | 应答是否需要注册 | 漏了会怎样 |
|---|---|---|
| 无回调（裸发） | **必须注册** | 每条回包刷一条 `guild cmd not register` 错误日志，且回包落 default 分支被丢弃 |
| 自定义回调里手动 dispatch | 必须注册 | 同上 |
| 带 callback 的模板版 | 可不注册 | 回包进自定义 CB，不进 dispatch |
| 空 callback（未赋值） | 可不注册 | 框架丢弃应答，不进 dispatch |

**三处注册表要对称核对**（新增命令时逐处确认）：

1. 公会服：handler 注册 + 应答注册（`sendResponse` 查 id 用）；
2. 网关：发起侧 `Req` 注册 +（无回调发送时）`Rsp` 注册；
3. 其它会发同类命令的进程：自己发过的 `Req` + 对应 `Rsp`。

**补应答注册必须同时补 handler**：注册宏会自动生成 handler 声明，缺实现链接失败。
fire-and-forget 场景 handler 只记失败日志即可。

### 目录即契约

- **`proto/client/` 下定义的每个 struct/字段，都是客户端↔服务器之间收发的协议内容。**
  往这里加字段，等价于**要求客户端去消费它**。
- 加字段前必须确认客户端真的会用：拿它显示什么 UI、驱动什么交互？说不出用途就不该加。
- **服务器自己要用但客户端不看的数据 → 放 `src/datastructs/`（Cache），不要放 `proto/client/`。**

### 关键宏机制（re-include 自动生成声明）

- `REGISTER_COMMAND(cmd, flagtype)`：一行宏，被 re-include 多次，**自动生成** CS/SC 前置声明、handler 声明、两条 cmdId 注册。你只写 handler 实现。
  - **flagtype：同步消息填 5，异步消息填 4。**
  - 判断依据：这条 CS 的 handler 会不会立刻回 SC？会 = 5，要等回调 = 4。
- `REGISTER_PUSH(type, time, storenum, cmd)`：拼 `CmdId_##cmd` + `Cmd_##cmd`（**不加 `_CS/_SC` 后缀**）。
  命名用 `Cmd_Push_Xxx`，宏参数传 `Push_Xxx`。
- `REGISTER_FORWARD(cmd)`：拼 `handleForward_##cmd(...)`。
  `REGISTER_FORWARD_RESP` 只生成 class 前置声明（回包结构无 handler）。
- 新增 `.cpp` 文件后要重跑构建系统，让它重新收集源文件。

## 二、CmdId 号段管理（最高频踩坑）

- **生成器/模板给的默认号段常撞车。** 不要信注释里写的"本段空闲"。
- **动手前必 grep 全库找真正空闲段**：

  ```
  grep -rho "= 71[0-9][0-9][0-9]" proto/client/*.idl | grep -o "71[0-9]*" | sort -n | uniq | tail
  ```

  取当前最大值往后开一个全新的 20~30 号区间（交互多的模块开 30）。

- 号段确认后同步改：IDL 顶部的号段注释、被 include 文件的号段注释。
- Forward 号段在 `forward.idl` 的枚举里单独排，同样 grep 确认。
- **未外放期间：删消息后号段立即压实回收，不留空号。**
  - 判据是**这个功能有没有外放**。
  - **没外放** → 删完重排成连续号，别"为将来预留"。CmdId 全走宏名注册，重排数字**零 C++ 改动**，只需重跑生成器。
  - **已外放** → 号段冻结：删消息只能留空号，新增只能取更大的号（同 struct 内的 tag 号同理）。

## 三、IDL 语法要点

```
#include "proto/client/structs.idl"      // 含公共结构 / 玩家标识

module GameProto {                        // 客户端消息用 GameProto；Inter/Forward 用 GameSvr
    enum CmdId_Act_Xxx { CmdId_Act_Xxx_Yyy_CS = N, ... };
    enum EXxxState { EXxxState_A = 0, ... };   // 业务枚举

    struct CmdXxx {
        0   optional unsigned int    iField;   // tag 从 0 起，同结构内唯一
        1   optional PlayerKey       stRole;
        2   optional vector<CmdSub>  vList;
        3   optional map<unsigned int, CmdSub> mMap;
    };
};
```

- **tag 号从 0 起连续填充，不要跳号/分段留空**（不要写成 0~4 然后跳到 10、20、30 分组）。
- tag 号**一旦上线**才不可复用/改序（删字段留空号、新增只能用更大的新 tag）。
  这与"首次定义连续填充"不冲突：**没上线随便重排，上线后才冻结**。
- **新增 tag 前必须查两处**：该结构的历史 tag、线上存储里该 tag 的实际类型。
  只看当前 IDL 不够——复用旧 tag 会导致反序列化失败。
- **IDL 与引用它的 cpp 必须原子提交。** 只撤字段不撤引用会让整批构建失败。
  提交后必须全量编译一次，不能只看单文件通过。
- 类型：`unsigned int`(uint32) / `unsigned long`(uint64) / `int` / `string` / `bool` / `vector<>` / `map<>`。
- `module` 选择：客户端协议用客户端 module；Inter/Forward 用内部 module。
  引用另一 module 的结构要加前缀。
- **引用别的 IDL 里的结构，必须 `#include` 那个文件**。解析器只认 include 闭包里的类型，缺了即
  `undefined struct type` + `fail to parse file`。
  - 集中放全项目推送的 `proto/client/push.idl` 最容易踩：新功能推送结构嵌了业务结构时，
    要在它的 include 列表补一行对应业务 IDL。
  - 加完顺手确认无环（被引文件不得反向引 `push.idl`）。

## 四、proto 结构 vs Cache 结构里的玩家标识

跨服玩家标识通常有两套结构，**字段一致（zoneId + uid）但类型不同，不能混用**：

- **proto 侧**（客户端消息 / Forward）：`GameProto::PlayerKey`
- **Cache 侧**（存盘 / 共享存储）：`CachePlayerKey`

在 `CacheXxx` 结构里存玩家 id **必须用 Cache 侧类型**，用 proto 的会编译错。
两者手动逐字段互转。

## 五、跨进程状态的既定载体（别自己造轮子）

新增跨服功能前，先复用这些既定机制：

### 共享存储（跨大区共享）

- 定义：公共类型枚举 + `makeKey(type, subKey)`。
  **切勿调整既有枚举顺序**，只在末尾加。
- 代理：仿已有的 `async_getXxx / setXxx` 加一对。
- 用途：按 **账号**（同账号跨服状态）或按 **业务实体 id**（如跨服聚合记录）存，任意服可读。
- 判断"该用共享存储还是本地"：跨服要共享 → 共享存储；落地本服后的进度/领取 → 本地 Cache。

### 跨服转发（给指定在线角色发 RPC）

- `FORWARD_MGR->sendAsync("", 目标zoneId, 目标uid, 本zoneId, 本uid, stReq, cb)`。
- 收端在 `handleForward_Xxx_Req`：`ROLE_MGR->getRoleByUid(zone, uid)` → 调 role 逻辑 → `sendResponse(stRsp)`。
- 回调基类：`AsyncContext<...Callback>`，实现 `callback_doGlobalForward` + `callback_doGlobalForward_exception`。
  即发即忘型可只记失败日志。
- **`DIR_MGR::checkLocalZone(zone, uid)`** 判断目标是否本地（本地直接调，远端才 forward）。

## 六、红线（违反会被打回）

### 1. 新增下发字段前，先做"冗余三连"

任一为是就不加：

1. **能不能从同一条消息里已有字段推导？** 能 → 不加，让客户端自己算。
2. **是不是通用层/别的接口已经下发了？** 是 → 不加。
   - 活动时间已在通用活动数据里 → 专属 Status 不再放；
   - 道具数量走通用道具推送 → 下注/发奖类消息不要再带余额。
3. **它是"客户端推不出的服务器权威状态"吗？** 只有这类才下发。

> 口诀：**下发权威既成状态，不下发派生展示值。**
> 服务端 Cache 内部可以存派生值，但那是内部数据，≠ 要下发。

**强制自检法**：定义每个下发字段时，行内注释末尾标"为何下发"——
`// 已领档位（权威：防重，客户端推不出）`。
写不出"为何客户端推不出"的字段，就是该删的派生字段。

**消息 struct 与 Cache struct 定位不同，各自独立精简，不要强行对齐**：
- 消息 struct = 给客户端：只放客户端推不出的权威状态。
- Cache struct = 服务端自用：逻辑需要什么就存什么，但**不必和消息字段一一对应**。

### 2. 下发字段必须声明时效语义

实时 / 事件快照 / 可推导三选一。
快照字段在注释里写清"哪个瞬间的快照"和"靠什么刷新/失效"。
展示口径与结算口径必须是同一份、同一时点。
字段在 Cache / 跨服快照 / 协议 / 战斗上下文之间有几份副本，先列副本谱系表
（见 `game-feature-playbook` 表 0）。

### 3. 消息契约

- **CS 有且仅有一条 SC**：即使结果为空也要回，否则客户端卡等；也不能回多条。
- **异步回调里回 SC，回调基类必须继承 `AsyncContext`**（做快照/恢复当前处理上下文），
  防止并发把 SC 发给错误的玩家。自定义回调 CB 必须继承它，不能裸用。

### 4. Push 专属判据

push 字段不能用"能从 Status / GetInit 推出来"来删。
push 的语义是"服务端状态刚变了、客户端手里那份快照**已经过期**"。

判据是**"客户端收到这条 push 的那一刻，能否用手里（不会过期的）数据算出来"**，而不是"字段之间能不能互相推"：

- **必须带**：本轮结果、是否被淘汰——客户端持有的是上一轮快照，本轮结果它根本不知道。
- **必须带**：连战场景的对手——取决于前一场结果，快照里没有。
- **别让客户端做枚举算术**：阶段枚举不保证连续，服务端自己都禁用这种下标运算 → 保留显式字段。
- **"可推 ≠ 该推"**：推导结论若是一条界面的输入契约，就保留。
  判据补一条：**推出来之后，客户端还得额外依赖另一份可能过期的数据/别的消息吗？** 要 → 保留。

### 5. 精简别砍出"弹窗没数据可弹"

删字段前先问"有没有一个界面/弹窗把它当输入"；
**但加之前更要问"那个界面要的数据，是不是另一条推送已经喂了"** —— 能靠既有推送解决，就别在首屏包里再造一份。

- **触发点决定挂在谁身上**：由客户端某次请求触发的事件，优先复用那次请求的回包；
  只有服务端自发发生的（定时结算、别人引发的状态变化）才需要独立 push。
- **限时奖励类交互，状态必须能"离线回填"**：只要一条奖励是"过了这村没这店"，
  就不能只靠 push 通知——玩家当时不在线，push 直接丢，重新上线连入口都找不到。
  做法：领取入口照旧是无参 CS/SC，但"有没有奖没领"的状态回填进首屏 SC（bool）。
  自检：**这条 push 丢了，玩家重新上线还找不找得回这个入口？**
- **"未读"类字段多半是伪需求**：先跟策划确认补弹口径（全补弹 / 只扑脸最近一次 + 其余走邮件），
  再决定要不要维护未读计数。

### 6. 主动推送只能走通用 push 通道

想让客户端感知服务器侧状态变化，改状态后调通用活动状态推送，客户端从刷新的 Status 感知；
**不要**为此单独定义一条 `Cmd_Xxx_Notify_SC` 之类的独立下推消息。
真正需要独立 push 的是全局级/非活动类推送，用 `Cmd_Push_Xxx` + `REGISTER_PUSH`。

### 7. 能合并的 CS 尽量合并

语义对偶的操作（接受/拒绝、开启/关闭）合成一条 CS，用 bool/enum 字段区分，不要开两条 cmdId。

## 七、错误码新增

- **续编该功能自己的号段，不要另起新段。** 先 grep 该前缀看段内最后已用号，+1。
- **不要写死"当前最大值"**。数字会变；写死会诱导借用别人的预留段。
- 命名 `Error_<功能>_<语义后缀>`，禁止功能内二级中缀。带一行注释。
- 号段不够优先合并语义相近的码；只回给玩家的码才需细分，内部/Forward 用能 `return 0` 就不单独占码。
- 新号确认用 `grep -n "= <拟用号>"`，不要用宽泛的最大值推断。

## 七点五、契约审计（文档 ↔ IDL 机械对账）

> 脚本与规则以 `game-feature-playbook` §2 为权威，本节只给协议侧用法。

消息指南与 IDL 长期漂移，人工核对必漏。交付前跑一次：

```bash
python "<skills>/game-feature-playbook/scripts/audit_message_contract.py" \
  --idl-dir "~/work/main/proto/client" \
  --doc "<消息指南.md>" \
  --prefix Cmd_Act_Xxx \
  --show-missing
```

必查两类：

- **幽灵项（FAIL）**：文档写了、IDL 没有。客户端按文档实现必然错。
- **遗漏项（WARN）**：IDL 有、文档没提。客户端可能不知道字段存在。

配套硬规则：

- **删字段留墓碑**：`// tagN 已废弃(rXXXXX)，禁止复用`；文档标"已删除，勿实现"。
- **号段复用必须记录**原用途 → 新用途 → 时间。
- **字段语义只写一次**（IDL 注释），文档引用不重解释。
  同一文档一处说"物理格号"、一处说"紧凑下标"，客户端按后者实现就会顶替错人。
- 语义变更（long→uint、含义变化）单列"破坏性变更"清单。

## 八、编译前置（改了 IDL 必做）

1. 改了任何 `.idl` → **重新生成 IDL→C++ 头**（新结构/新 cmdId 的 C++ 头才会出现在 `build/`）。
2. 新增了 `.cpp` → **重跑构建系统**刷新源文件收集。
3. 编译对应 Server。
4. **在干净检出上再编译一次**：本地工作副本能编，不代表干净代码能编。
   经典事故：IDL 漏提交，本地有生成物、干净检出后整批编译失败。
5. 自检：grep 确认 cmdId/ForwardId 无重复、Cache 里无 proto 侧标识误用、花括号配平。

## 八点五、离线回填（有 Push 就必须有首屏）

任何"状态变化时推送"的功能，必须同时写入以下三条，否则玩家离线期间的变更会永久丢：

1. 功能自己的 `GetInit_SC`；
2. 登录首屏 `Role_Init_SC` 或其附带的红点/状态字段；
3. 重新登录后的主动拉取入口（不能只靠 push）。

判据：把玩家踢下线 → 改状态 → 重登，屏幕上必须能恢复到正确状态；只测在线 push 不算通过。
