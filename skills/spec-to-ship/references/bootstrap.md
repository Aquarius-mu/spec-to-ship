# 迁移到新代码库（Bootstrap）

> 目标：在一台新机器 / 新仓库上，把整套流程跑起来。
> 只换三样东西：**项目画像**、**项目铁律**、**项目示例**。方法论不动。

---

## 零、先分清四层（决定要改什么）

| 层 | 内容 | 换项目要不要改 |
|---|---|---|
| **L1 方法论** | 七阶段、进度声明、门禁、覆盖对账、消息减法思路 | ❌ 不动 |
| **L2 领域** | 客户端-服务端交互、离线/重连/跨进程、发奖扣费 | ⚠️ 若新项目不是这类，删掉无关章节 |
| **L3 技术栈** | 语言、构建、协议文件格式、日志格式、提交系统 | ✅ 填进 profile |
| **L4 仓库** | 具体路径、表名、函数名、专有铁律 | ✅ 填进 profile + pitfalls |

**只有 L3/L4 需要动。** 方法论不需要重新设计。

---

## 零之前、第一步：先验依赖（最容易漏）

这套流程不是单个 skill，是 **6 个 skill + 7 个 agent + 2 个脚本**。
只拷 `spec-to-ship` 会跑到第 ③ 步直接断。

```bash
python skills/spec-to-ship/scripts/check_deps.py
```

清单、拷贝命令、哪些缓存不要带、断了会在哪一步暴露 —— 全在 `porting.md`。

**依赖不齐，后面的步骤都是白做。**

## 一、五个步骤

### Step 1 —— 摸清代码根（不改任何东西）

```bash
# 找仓库
ls /            # 或对应盘符
find . -maxdepth 2 -name ".svn" -o -name ".git"
```

要确认的三件事：
1. 有几个仓 / 几个分支，各自放什么
2. 哪个是**当前要改的**
3. 有没有"本地副本过旧、必须走远端"这类限制

**证据**：`svn info` / `git remote -v` 能跑通，且分支名对得上。

---

### Step 2 —— 摸清构建链

```bash
find . -maxdepth 2 \( -name "Makefile" -o -name "CMakeLists.txt" -o -name "*.sln" -o -name "package.json" -o -name "go.mod" \)
```

要确认：
- 编译命令（**问用户要不要我编译**——很多项目明确要求用户自己编译）
- 产物路径
- 单次编译耗时（决定要不要后台跑）
- 发布命令

**证据**：编译命令在 profile 里写成一个能直接复制的完整命令。
**不要**凭猜测写 `make`——先看仓库里脚本叫什么。

---

### Step 3 —— 摸清协议层

```bash
# 找协议定义
grep -rl "struct Cmd_\|message .*Request\|interface .*Req" --include="*.IDL" --include="*.proto" --include="*.ts" --include="*.go" . | head
```

要确认：

| 问题 | 怎么回答 |
|---|---|
| 客户端协议放哪 | 找到目录，看命名规律 |
| 服务端自用结构放哪 | 通常在 `Cache`/`DataStructs`/`internal` 下 |
| 消息命名约定 | 抄 3 个真实消息名，别自己编格式 |
| 号段从哪查 | 找注册文件、看注释 |
| 已发布是否冻结 | **问用户或查发布记录**，这条猜错代价极高 |

**证据**：profile 里能写出 3 个真实存在的消息名，且能指出它们在哪个文件。

---

### Step 4 —— 摸清日志与验收证据

这一步最关键，因为**验收全靠它**。

```bash
# 找日志目录
ls /var/log/game 2>/dev/null || ls ./logs 2>/dev/null || find . -maxdepth 3 -name "*.log" | head
```

要分清两种证据（**很多项目会把它们混在一起，混了就等于没验收**）：

| 证据 | 回答什么问题 | 在你们项目里是什么 |
|---|---|---|
| **收包证据** | 服务端**真的收到**请求了吗 | |
| **回包证据** | 客户端**真的收到**应答了吗 | |

**最常见的坑**：拿收包日志当回包证据——只看到"收到"，看不到"回没回"。
**证据**：profile 里两个都填了具体文件名/命令，且能实际打开一个文件看到样例行。

---

### Step 5 —— 摸清调试工具

| 工具 | 要确认 |
|---|---|
| GM / 后台 | 入口在哪、怎么发一条命令 |
| 消息探针 | 能不能自己发一条请求、收推送 |
| 造数据 | 怎么造出可测状态 |
| 端到端范式 | 有没有现成的可抄 |

**证据**：能实际发出一条 GM 命令并拿到返回。

## 一点五、填画像的三条铁律

迁移演练实测暴露过的问题，先记住：

| 禁止 | 为什么 | 改成 |
|---|---|---|
| 填裸版本号 | "format 12" 和 "format 29" 可能都对，指的是不同东西 | 写**现象 + 后果 + 怎么办**："本地 svn 客户端报 E155036，必须 ssh 到远端执行" |
| 填"应该是" | 没实测过的命令，跑起来必挂 | 实际执行一次，或明确写"未验证" |
| 填通用道理 | "要注意安全" 等于没填 | 只写这个仓库特有的（"拆文件必须补 include，因为 unity build"） |

**自检脚本只验结构，不验真假。** 内容对不对，只能靠 §十 检查表逐条实地确认。

## 二、填完之后必须自检

```bash
python scripts/check_profile.py references/profile/<你的项目>.md
```

检查项：
- 十个章节没有留空
- 换项目检查表全部打勾
- 关键字段不是占位符

**不通过就不许开跑**——带着半空的画像跑，等于回到"凭猜"。

---

## 三、项目铁律怎么攒（不用一次到位）

第一次迁移时，铁律可能只有 3 条。这没关系。

**攒法**：每踩一个新坑，当天追加一条到 `codebase-pitfalls.md`：

```
现象：<报错原文>
后果：<什么坏了>
正确做法：<下次怎么做>
```

**不要写通用道理**（"要小心"），只写**这个仓库特有**的（"拆文件后必须补 include，因为是 unity build"）。

## 五、迁移后跑一次冒烟

不要一上来就跑完整案子。先跑这三条，确认链路通：

| 冒烟项 | 做什么 | 通过判据 |
|---|---|---|
| **读案** | 读一个真实飞书案子的正文 + 评论 | 拿到字符数、评论条数 |
| **定位** | 在代码里 grep 一个真实存在的消息名 | 命中文件 + 行号 |
| **取证** | 打开一条日志，找到一条 `recv cmd` 样例 | 看到真实命令行 |

三条都过，说明 L3 通了。再跑完整案子。

## 六、什么时候该收手

出现以下情况，说明新项目不适合直接套这套流程：

| 情况 | 怎么办 |
|---|---|
| 没有"客户端-服务端交互" | 删掉 ④ 协议阶段，其余保留 |
| 没有可达的测试环境 | 验收降级为 `[推断]`，交付时明确标注 |
| 没有日志/监控 | 必须先补可观测性，否则验收无法取证 |
| 需求源不是飞书 | 把 ① 读案换成对应的读取方式，其余不变 |
