## 一、这套流程从哪来（为什么可信）

不是设计出来的，是**从真实返工里反推的**。

| 语料 | 规模 |
|---|---|
| AI 编码会话正文 | 数百段会话 / 十万行量级 |
| 另一套 AI 助手的归档 | 完整过程记录 |
| 编辑器内置 AI 的用户发言 | 数百条 |
| 历史输入与早期索引 | 数百条（早期仅存标题） |

分析方式：把每段会话还原成**完整过程链**（用户原话 → 工具调用 → 错误 → 助手说明），而不是只留头尾。
共切出上千个事件链，逐条归类成"发生链条 → 防呆规则"。

**数据边界（必须知道）**：早期只有会话标题、正文已不在本地；跨工具的记录不连续。
所以规则只写**跨工具都成立**的部分，不写某个工具的特有细节。

## 二、S0 锁事实源

**目的**：在写第一行代码前，把"什么是对的"钉死。

| 要锁什么 | 怎么锁 | 锁不住会怎样 |
|---|---|---|
| 案子链接 | wiki 先取 `obj_token` | 读到旧版本 |
| 案子版本 | 读版本历史 / revision，记日期 | 策划改了不知道 |
| 代码根 | 具体到哪个仓库/哪个分支（本项目路径见 `profile/<项目>.md` §二） | **改错仓库**（实踩：代码路径错，白干） |
| 范围 | 全部 / 某人负责部分 / 需求单号 | 漏做或越界 |
| 环境 | 内网 dev / 阿里云 / 外网，各对应哪台机 | 在内网查外网问题 |

**门禁**：五项都写下具体值，写不出就问用户一次问清。

## 三、S1 读案（六类载体，缺一即未读完）

### 3.1 读什么

| 载体 | 怎么读 | 为什么必读 |
|---|---|---|
| 正文 | `lark-cli docs +fetch --doc <obj_token>` | 主需求 |
| 内嵌表/Base | `lark-cli sheets +csv-get --sheet-id <id>` | **数值只在表里**，正文从不写全 |
| 画板/画格 | `lark-whiteboard` 导出节点 | 流程图/状态图常是唯一需求源 |
| 正文图片 | 导出后看图 | UI 截图里的文案和布局 |
| 评论区 | `lark-cli drive +list-comments --url <url> --solved-status all` | **策划的修正都在这里** |
| 修订历史 | 读版本记录 | 判断是否最新 |

### 3.2 实测数据（某大型活动一期案子）

| 载体 | 数量 | 结果 |
|---|---|---|
| 正文 | 34,373 字符 / 50 个标题 | ✅ |
| 内嵌表 | 4 张（科技 14×26、等级 9×9、增益道具 6×4） | ✅ |
| 画板 | 14 个 | ✅ 全导出，2 个纯图片 |
| 评论 | 20 条 | ✅ **5 条直接推翻正文** |
| 空章节 | 6 个 | ✅ 记为缺口 |

**评论推翻的 5 条**（只读正文必然做错）：
1. 删除示例玩法
2. 周日只开两轮（画板写 3 轮）
3. 玩家可离开公会，不改变阵营归属
4. 防守胜利不加分
5. 21 点开始结算（正文/画板写 19:30）

### 3.3 门禁
- 六类都有记录；读不到的写明原因
- 空章节逐条记缺口
- 正文 vs 表 vs 画板 vs 评论的冲突，原样列两边，不自行选一边

## 四、S2 需求清单（R-xx）

### 4.1 写法

每条一个可验收断言：

```
R-07 [P1] 来源:正文§2.1 / 表t_xxx第3行
  WHEN 玩家占领示例资源点到期 → 系统 SHALL 结算并发放对应奖励
  IF 玩家离线 → THEN 走邮件补发
  验收: Given 前置 When 操作 Then 可观测结果
```

### 4.2 硬规则

| 规则 | 原因 |
|---|---|
| 编号 `R-xx` 永不复用 | 删了标"已删除"，改号会让追溯断链 |
| **每 20 条增量落盘** | 实测：大案一次性生成会超时，中断全丢 |
| 每条有出处锚点 | 没有出处的值就是臆造 |
| 模糊词命中即进缺口 | "一些/尽量/合理/等" = 未闭合需求 |
| **评论优先于正文** | 评论是最新口径 |

### 4.3 产出三份文件

```
.tmpfiles/<功能>/
  需求规格.md    R-xx + 出处 + 可验证点
  已决台账.md    D-xx（用户/策划答过的，跨会话复用）
  缺口清单.md    Q-xx（七路检索后仍无解的）
```

**下游只读这三份，不再访问飞书。**

## 五、S3 缺口裁决（七路检索）

问人之前必须跑完七路：**正文 → 画板 → 内嵌表 → 关联文档 → 配置表 → 历史/台账 → 代码先例**。

七路全空才允许问，且一次问清。每条缺口带：
- 问题
- 已查七路的结果
- 建议默认值
- 为什么阻塞

**禁止**：案子已写还问；用户已答还问；只查到一半就整条抛回。

## 六、S4 字段映射（最容易被跳过，也最容易翻车）

**凡案子画了界面 / 列了表头，必做。**

| 案子字段 | 文本id | 协议字段 | 数据来源 | 结论 |
|---|---|---|---|---|
| 公会名称 | STRID_xxx_Guild | vRank[].sGuildName | stBaseInfo.sGuild | 已实现 |
| 击杀士兵数 | STRID_xxx_KilledSoldiers | vRank[].iRankValue2 | <结构体>.iKillSoldier | 缺 |

> 第二列是本项目文案 id、第四列是实际结构体字段（本项目示例见 `profile/example-project.md` §四）。

**判据：每行有结论，"缺"的行数必须为 0 才能交付。**

数据来源要写到**具体结构体字段**，不能写"已有接口"。

**实踩**：排行榜玩法排行榜案子明列 6 列，直接读代码发现联盟为空就去补，没先对照案子，被指出"案子明明写了，为什么还是没有"。

#### S4 的两种情形（回归实测发现）

| 情形 | 顺序 | 说明 |
|---|---|---|
| **改造已有功能** | S4 → S5 | 有现成协议可映射 |
| **全新功能** | S4（列字段）→ **S5 先立协议骨架** → 回到 S4 填映射 | 代码侧无落点，映射表 92% 是"缺" |

实测：某大型活动一期案子里 211 个界面字段，`已实现 0 / 缺 194 / 待查 17`——因为全仓没有任何阵营/排行榜玩法/增益道具协议。

**所以全新功能时，S4 第一次只产出"新增字段清单"，等 S5 定完 CmdId 与结构体名才能填满映射表。** 不要卡在 S4 硬填。

## 七、S5 协议设计（先做减法）

### 7.1 字段五问（任一为是就删）

1. **客户端能不能用已有字段算出来？**
   - `bStartSoon` = `iStageEndSec - now <= 180`
   - 胜负 = `iWinnerGuildId != 0`
   - 列表条数 = `vList.size()`
2. **策划表里有没有？** 名称/奖励/上限/消耗/概率 → 客户端读表
3. **别的消息是否已下发？** 排行榜走通用榜；道具数量走 `Cmd_Push_SetItem`
4. **是不是客户端自己刚发的回显？** 只有多 `iType` 复用或分页才留
5. 只有 1–4 全否（服务端权威既成状态）才下发

### 7.2 其他硬规则

| 规则 | 反例 |
|---|---|
| `iTotal/iOffset` 只在真分页时保留 | ≤十几条的列表不分页 |
| 操作码用 `enum` | `iOper = 1..6` 裸数字被打回 |
| 内部动作不进 CS 值域 | 刷新快照塞进 `iOper` |
| `Status` 只放零成本状态 | 跨进程/排序/聚合走查询消息 |
| 已落盘 tag/类型不可改 | 复用 tag 21 改类型 → 整图 MapNotFound |
| 未外放就压实 0..N | 留空号被指出多次 |
| CS 每个分支恰好一条 SC | 框架回一次 + handler 再回一次 = 重复包 |

### 7.3 门禁
跑 `game-feature-playbook/scripts/audit_message_contract.py`，文档↔IDL 零幽灵。

## 九、S7 实现

### 9.1 顺序（按玩家旅程）

入口 → 准备 → 进行 → 结算 → 清理

### 9.2 硬规则

| 规则 | 事故 |
|---|---|
| **先判定后写入** | 先写 `iStage` 再判等 → 副作用整段死代码 |
| **先校验后落库** | 先持久化再校验 → 重复英雄泄漏到跨服 |
| **状态四联动** | 写 cache + `setChanged` + push + 日志，缺一不可 |
| **配对完整** | 扣费↔退款、报名↔撤报名、发奖↔去重 |
| **跨服三禁** | 禁本区兜底、禁裁快照字段、禁跨库直写 |
| **未外放不兼容** | 不写迁移/补档 |
| **幂等键要全** | `mapId + round + settleId/eventId`，只用 settleId 会撞号吞奖 |
| **先写幂等键再发奖** | 先置位后发 → 失败永久漏发 |

### 9.3 代码质量（返工主因）

见 `code-quality.md`。核心：
- 文件不要拆
- 头文件要减
- 变量能省则省
- 注释一句话 ≤20 字、禁行尾
- 改动覆盖需求单**全部提交**
- 禁止表面优化：交付必须写"删了什么/合并了什么/行数变化"

## 十、S8 自检（交付前必做）

### 10.1 自评分（5 项，每项 0–2）

| 项 | 0 分 | 2 分 |
|---|---|---|
| 消息字段必要性 | 有可删的 | 每个字段都能说出客户端为什么不能算 |
| 代码冗余 | 有明显重复 | 重复已合并，变量已省 |
| 头文件与存储 | 存了不该存的 | 能算的不存 |
| 注释 | 有行尾/废话 | 一句话、说为什么 |
| 改动完整性 | 只看最新 diff | 覆盖需求单全部提交 |

**低于 8 分不许交付。**

### 10.2 独立证伪

派一个 agent，让它找"**哪里还能删 / 哪里删错了**"，不是问"对不对"。

## 十二、S10 验收

### 12.1 协议实测的四条铁证（缺一条 = 没跑）

**凡有客户端协议，"跑过了"必须同时交出这四样**：

| # | 证据 | 从哪取 | 证明什么 |
|---|---|---|---|
| ① | **CS 发出原文** | 探针 lua 脚本 / 探针输出 | 我发了什么、参数是什么 |
| ② | **服务端收包行** | `game.GameServer_commandstr_*.log` 里的 `recv cmd: Cmd_Xxx_CS` | 服务端**真收到了**，不是本地空转 |
| ③ | **SC 回包原文** | 探针输出里的 `send response: Cmd_Xxx_SC` 段 | 玩家**真收到**了反馈 |
| ④ | **回包字段判读** | 逐字段对照 R-xx 的期望值 | 内容**对不对** |

**⚠️ 两个概念别混**：
- `commandstr` 日志记的是**服务端收到的命令**（`recv cmd`），**不是回包**。
- 回包在探针输出 / `send response`。**只看 commandstr 会永远发现不了"回包是空的"。**

同一请求通常成对出现：`recv cmd` 紧跟 `send response`。
- **只有 recv 没有 response = CS 没回 SC（P0）**
- **两者都没有 = 这条压根没发**（只跑了 GM 编排）

### 12.2 空回包不是 PASS，是待判

| 情况 | 判据 | 结论 |
|---|---|---|
| **合法空** | 需求明确此处可以没数据（如首次进入无排行） | PASS，但必须写"空是预期的，依据 §x.y" |
| **异常空** | 该有数据却回空（列表长度 0、关键字段 0、id 为 0） | **FAIL** |
| **没有回包** | 探针从无 `send response` | **P0** |

> "回包是空的"不能当"跑过了"。写不出预期依据的，一律按 FAIL。

### 12.3 三路交叉

① 回包 ② 服务端状态（GM 回读 / DB）③ 玩家可见效果（推送是否到达）。

**回包 ok ≠ 状态生效 ≠ 玩家看到。** 三路里两路打架 = 还有没查出来的问题。

### 12.4 必查项

- 生命周期 10 时刻
- 多身份交叉（施害方/受害方/旁观者）
- 跨进程通道
- 并发/重复点击/离线/重登/重启
- 跨周期清理

### 12.5 结论标注

每条标 `[实测]` 或 `[推断]`；混在一起 = 报告作废。

**源码已修但未部署 = FAIL。**

## 十四、常见失败与应对

| 失败 | 表现 | 应对 |
|---|---|---|
| 只看头尾 | 漏掉"修复引出新 bug"的链条 | 读完整过程链 |
| 抽样冒充全量 | "我看了所有" 实际只看几条 | 给覆盖范围、总数、时间区间 |
| 臆造配置 | 案子没有的 key | 每个值必须有出处 |
| 接线当实现 | 注册了 handler 就算完成 | 打开实现确认语义 |
| 表面优化 | 说"已优化"但说不出删了什么 | 强制写三项变化 |
| 上下文丢失 | 跑一半忘了前面 | STATE.md 每阶段落盘 |
| 用陈旧缓存判断 | 文件实际变了但判定没变 | 读内容，不看 size |

## 十五、轻/中/重怎么选
