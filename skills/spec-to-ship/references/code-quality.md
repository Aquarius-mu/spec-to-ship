# 代码质量硬规则（来自 近百条返工反馈）

> 用户原话："每次改出来的代码都要再优化一遍，问题很多。"
> 证据分布：要求优化 25 ｜ 要求精简 22 ｜ 要求可读性 13 ｜ 指出质量差 12 ｜ 要求重写 9。
> 返工证据原文存放在本仓库证据目录（路径见 `profile/<项目>.md`）。
> **本文件在 G4 实现阶段必读；写任何消息/结构体/函数前先过一遍。**

## 0. 返工的真实原因（不是写错，是写脏）

绝大多数返工不是逻辑 bug，而是：

| 类型 | 用户原话 |
|---|---|
| 消息冗余 | "iTotal/iOffset/iRet 这个不是客户端的事情吗" ｜ "bStartSoon 客户端可以自己通过时间换算出来啊" ｜ （措辞已略） |
| 代码冗余 | "（措辞已略）" |
| 头文件膨胀 | "头文件里的成员变量为什么要有？内存很紧张，.h 必须减少" |
| 乱拆文件 | "文件不要拆分，要的是代码简洁" |
| 表面优化 | "只是表面优化" ｜ "不要局限于表现，要深入修复" |
| 注释啰嗦 | "注释要精简" ｜ "注释太多了，请你之后写的时候都做到注释精简" |
| 改动不全 | "你每次修改都是按照所有代码，也就是这次的所有提交去给我进行修改" ｜ "所有 svn 提交都修改一下" |
| 序号没压实 | "功能没有外放，序号可以继承" |
| 机翻腔 | "术语不符合中文语境" ｜ "介绍像机翻" |

## 1. 消息与协议：先做减法，再做功能

**每个字段按顺序问，任一是就删：**

1. 客户端能不能用已有字段算出来？
   - `bStartSoon` = `iStageEndSec - now <= 180` → 删
   - 胜负 = `iWinnerGuildId != 0` → 删
   - 列表条数 = `vList.size()` → 删
   - 已领状态看列表元素自带的 `bClaimed` → 聚合计数删
2. 策划表里有没有？名称/奖励/上限/消耗/概率 → 客户端读表 → 删
3. 别的消息/推送是否已经下发？
   - 排行榜 → 走通用榜 `Cmd_Rank_Role_CS`
   - 奖励预览 → 客户端读表
   - 道具数量 → `Cmd_Push_SetItem` 已带最新值
4. 是不是客户端自己刚发的参数回显？→ 只有多 `iType` 复用同一条 SC、或分页才留
5. 只有 1–4 全否（服务端权威既成状态）才下发

**更多具体规则：**
- `iTotal/iOffset` 只在真分页时保留；≤ 十几条的固定列表不分页
- `iRet` 不要塞在每条 SC 里，走统一错误通道
- 操作码用 `enum`，禁裸数字；服务器自己的动作（刷新快照、修正状态）不进客户端 CS 的值域
- `Status` 只放 GameServer 内存零成本拿到的状态；跨进程/排序/聚合走查询消息
- 同一语义只保留一个来源

## 2. 代码结构：能删就删

**顺序：先减，再拆，最后才加。**

1. **文件不要拆**。用户明确讨厌拆成多个小文件。按职责放在已有的对应文件里。
2. **头文件要减**。新增成员变量前问：这个值存下来谁读？读几次？能算出来吗？
   - 只读一次就不再用的中间量 → 不存
   - 能由配置/时间算出的 → 不存
   - map 的 key 已表达的 → 不重复存（`map<districtId, T>` 里的 `T.iDistrictId`）
3. **变量能省则省**。多余的局部变量、可内联的临时量、重复的判断，全砍。
4. **重复段落合并**。同一规则在三处手写 → 抽一个函数，只留一处。
5. **耦合要低、接口要抽**。但抽的是"职责"，不是"行数"。
6. **不要过度防御**。游戏数据有上限约束，不为不可能发生的输入加溢出保护。
7. **函数超 ~80 行或单段超 ~20 行，先拆再加**。

**删完必须验证**：导致"删了不该删的"比"没删"更糟。删字段/分支前先全库 grep 消费者。

## 3. 注释：一句话，说为什么

- **一句话，≤20 字**
- **禁止行尾注释**
- 写"为什么这么做/别人会踩什么坑"，不复述代码在干嘛
- 不写背景、不写长链路说明
- CmdId 行只写"查什么/干什么" + 参数枚举

反例（被打回）：
```cpp
// 这里我们遍历所有玩家，因为需要检查每个玩家的状态是否满足条件，然后更新
```
正例：
```cpp
// 离线玩家不回包，必须超时清理
```

## 4. 改动范围：按需求单全部提交，不是只看最新 diff

用户原话："你每次修改都是按照所有代码，也就是这次的所有提交去给我进行修改。"

- 拿到需求单号 → 先按单号搜提交历史，找出全部 revision（命令见 `profile/<项目>.md` §五）
- 按 revision 区间收集文件，不是只看工作副本未提交改动
- 同类问题横向清查：改了一处校验，同构的地方一起看

## 5. 序号与结构体：未外放就压实

- 未外放 → 删字段后立刻重排 `0..N` 连续，不留空号
- 已外放 → tag/类型冻结，删字段留墓碑注释
- 改完跑脚本校验重号/跳号/乱序

## 6. 禁止"表面优化"

用户原话："你只是表面优化……这些内容都是你的臆想。"

**不许说"已优化"，必须给可验证的变化：**
- 删了哪些字段/变量/分支（列出名字）
- 合并了哪几处重复（列出位置）
- 行数变化（前 → 后）
- 行为是否变化（应当为零，除非需求要求）

写不出这三项，就是没做。

## 7. 交付前自我辩证 + 打分

用户多次要求："给我开子 agent 自我辩证，深入去挖掘，不要局限于表现" ／ "修改方案出来之后自己打分"。

**流程：**
1. 改完先自评 5 项，每项 0–2 分，写进交付说明：
   - 消息字段必要性（有没有可删的）
   - 代码冗余（有没有可合并/可删的）
   - 头文件与存储（有没有不该存的）
   - 注释质量（是否一句话、无行尾）
   - 改动完整性（是否覆盖该需求单全部提交）
2. 低于 8 分不许交付，先自己改。
3. 重要改动派一个独立 agent 做"证伪"：让它找"哪里还能删""哪里删错了"，而不是"对不对"。

## 8. 中文与表达

- skill/文档必须是母语中文，不出现机翻式表达（"构建墙钟"这类）
- 数字、单位、时间写全，不用缩写糊弄
- 面向用户的说明先给结论，再给依据
