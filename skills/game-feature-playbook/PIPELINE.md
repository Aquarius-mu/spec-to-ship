# 从飞书案子到交付：全流程串联

> 这份文件只回答一件事：**手上有一个案子，接下来每一步用谁、产出什么、什么算过了。**
> 各 skill 的内容不在这里重复，只给入口和判据。

---

> 每个 skill 的适用边界、重叠归属、换项目要改什么，见根目录 [`README.md`](../../README.md)。

## 一张图

```
⓪入口        spec-to-ship   → 锁案 + 全流程门禁（一句话触发）
①读案子      case-reader        → 需求规格.md（R-xx）+ 已决台账 + 缺口清单
②开工定义    game-feature-playbook → 六张表（含副本谱系）+ 协议契约
③写协议      spec-to-ship ③④（设计）+ game-message-protocol（写法）→ IDL / 注册 / handler
④写逻辑      activity-editor 或项目 skill → 业务代码
⑤自审        game-code-review + 双 agent → 需求覆盖 + 玩家行为
⑥验收        adversarial-gameplay-acceptance → 实测 + 修复闭环
⑦交付        覆盖对账 100% + 12 问自证（spec-to-ship）
```

**顺序不可跳**：跳过 ①，后面全在猜；跳过 ②，代码会反复改；跳过 ⑥，bug 留给玩家。
**一句话触发**：直接说"帮我完成案子 <链接>"，`spec-to-ship` 会串起 ⓪→⑦ 全程。

---

## ① 读案子（一次性，别重复读）

**用**：`.claude/agents/case-reader.md`（agent），或手动照它的规则读。

**必须读全五类载体**（缺一类就是没读完）：

| 载体 | 判据 |
|---|---|
| 正文 | 一级到末级标题全部过 |
| 画板 | 每个 `<whiteboard token>` 都导出；图上有正文没有的，单独记 |
| 内嵌表 / Base | 每个 `<sheet token>` 都读；数值逐档誊，不许写"详见原表" |
| 评论 / 修订 | 与正文冲突时取最新并标注 |
| 空章节 | 标题空 = 一条需求缺口，必须记 |

**产出三份，落在 `.tmpfiles/<功能>/`**：

```
需求规格.md    R-xx 条目（编号永不复用）+ 出处 + 可验证点
已决台账.md    D-xx（用户/策划答过的问题，跨会话复用）
缺口清单.md    Q-xx（七路检索后仍无解的，才允许问人）
```

**判据**：每条需求都有 `R-xx` 和出处；问人的问题都能说出"七路查了什么"。

> **别让第二个 skill 再读一遍案子**——后面所有人只读这三份文件。

## ② 开工定义（缺一不许写代码）

**用**：`game-feature-playbook`

从 `需求规格.md` 推出六张表：

| 表 | 输入来自 | 不填的后果 |
|---|---|---|
| 副本谱系与时效契约（表 0） | 每个跨模块消费/下发的字段 | 展示与结算各用一份、快照不刷新、加成写晚没展开 |
| 状态生命周期矩阵 | 每个会变的字段 | 初始/离线/重登/重启/跨周期全漏 |
| ID 域表 | 每个跨函数传的 id | 取消 A 误取消 B |
| 上限表 | 每个"最多/最多可" | 边界算错，5/4 还能加 |
| 变更→推送表 | 每个写操作 | 改完不刷新 |
| 消息契约表 | 每个玩家动作 | 消息反复改 |
| **UI 字段映射表** | **方案里每个界面列出的每个字段** | **有列名没数据，客户端整列空着** |

**UI 字段映射表**必须一行一案子字段，五列写全：

| 案子字段 | 文本id | 协议字段 | 数据来源 | 结论 |
|---|---|---|---|---|
| 公会 | STRID_COCMap_Guild | vRank[].sGuildName | stBaseInfo.sGuild | 已实现 / 缺 / 客户端自算 |

**判据**：写完自问——"换个人只看这七张表，能不能实现得和我一样？"能，才算定义完成。
另：字段映射表的"缺"必须清零才能进 ④；不能等审查阶段才发现整列没数据。
实踩：排行榜玩法排行榜方案列了 6 列，实现时按代码现状只补了"看起来缺"的字段，公会列整列空着，被用户当场指出。

## ③ 写协议

**用**：`game-message-protocol`

规则：**一个玩家动作 = 一条请求**；操作码用枚举；内部动作不进客户端协议；字段先问"谁能删"。

**判据**：跑一次 `game-feature-playbook/scripts/audit_message_contract.py`，
文档与 IDL 零幽灵项（文档有、IDL 没有）。

---

## ④ 写逻辑

**用**：`activity-editor`（活动类）或项目 skill（如 `example-s3-dev`）。

**每落一个写入点，回填表 1、表 4；每加一个字段，回填表 2、表 5。**

实现顺序按玩家旅程：入口 → 准备 → 进行 → 结算 → 清理。

## ⑤ 自审（两道，不许自己审自己）

| 审查 | 用什么 | 查什么 |
|---|---|---|
| 代码质量 | `game-code-review` | 规范、配对、安全、可读性 |
| 需求覆盖 | 独立 agent A | 逐条 `R-xx → file:line`：已实现 / 未实现 / 偏差 |
| 玩家行为 | 独立 agent B（只看需求不看码） | 从进活动走到结算，哪一步走不通 |

**判据**：P0 断点清零；R-xx 每条有结论。

## ⑥ 验收

**用**：`adversarial-gameplay-acceptance`

### 怎么发起

写完代码后，说一句触发词即可：

| 你说 | 触发什么 | 覆盖范围 |
|---|---|---|
| **"总体验收"** / **"收工验收"** / **"上线前验一遍"** | 功能级完整验收 | **全部 R-xx + 全部消息 + 全部玩家身份 + 生命周期 10 时刻** |
| "验一下这个 XX" / "验收一下" | 单点验收 | 该点 + 受影响分支 |
| "复核 / 再审一下上次报告" | 复验 | 上一轮 FAIL + 受影响条目 |

**总体验收会做什么**（不需要你再交代）：

```
1. 读 .tmpfiles/<功能>/{需求规格,已决台账,缺口清单}.md（没有则先退回读案子）
2. 按 R-xx 逐条验，不抽样、不用"主流程跑通"概括
3. 每条落到：PASS / FAIL / 待外部输入 / 明确不做
4. FAIL 走修复闭环：定位 → 改码 → 编译 → 发服 → 重测
5. 出总报告 + 覆盖表 + 待外部输入清单
```

**验收必查四类**：生命周期 10 时刻（初始/离线/重登/重启/跨周期/并发…）、
多身份交叉（施害方/受害方/旁观者）、跨进程通道（下发/回拉/转发/大块数据）、赛季或周期清理。

### 你要提供的（只有两件）

| 事项 | 什么时候需要 |
|---|---|
| **编译 / 发服授权** | 首次；之后同会话沿用，但每次发服会记进环境指纹 |
| **靶场信息**（若还没存进 `project-anchors.md`） | 首次；存过就不再问 |

### 你会拿到的

1. 每条 R-xx 的结论（PASS / FAIL / 待外部输入 / 不做），一行一条；
2. 每个 FAIL 的完整链条：分诊 → 修复 → 复跑 → 复测通过；
3. 待外部输入清单（策划表、文案、客户端字段、策划决策）；
4. 形式闸门通过的报告（`verify_report.py` 校验过）；
5. 未验证项与原因，不糊。

### 对齐点（不重复做）

| 验收 skill 说的 | 本流水线对应的产物 |
|---|---|
| Step -1 需求锚定 | ① 的三份文件，直接读 |
| 代码地图 / 消息清单 | ③ ④ 的产出 |
| 双向对账 | ② 的六张表（含表 0）+ ⑤ 的覆盖表 |

**判据**：每个 FAIL 都走完修复闭环并复测通过；连续两轮 FAIL 不变 = 熔断复盘。

---

## ⑦ 交付

必须交出：

1. `R-xx → 实现位置 → 结论` 覆盖表（100% 行数）；
2. **UI 字段映射表逐行结论**（案子字段 → 协议字段 → 数据来源），缺项必须先清零；
3. 待外部输入清单（表 / 文案 / 客户端字段 / 策划决策）；
3. 文档回写（改了什么，甲方看的那份要同步）；
4. 未验证项，如实标注。

```
按这个案子开发：<飞书链接>

严格按 PIPELINE 走：

2. 再按 game-feature-playbook 填六张表（含表 0 副本谱系）

- 每个问题先跑七路检索（正文/画板/内嵌表/关联文档/配置/历史/代码），
  七路全空才来问我，且一次问清
- 说"做完了"必须给：改了哪些文件 + 对应 R-xx + 怎么验证的
- 不要重复读案子，后面只读那三份文件
```

## 三处已知重叠（按此处理）

| 重叠 | 处理 |
|---|---|
| 读案与列清单 | **只走 case-reader**；`spec-to-ship` 与 `spec-driven-dev` 都只读产出的三份文件，不重复读飞书 |
| `spec-to-ship` 与 `spec-driven-dev` 分工 | 前者管读案、选档、验收、交付；后者管字段映射、消息减法、实现、双 agent、覆盖对账。**规则只在后者写一份** |
| 状态生命周期矩阵在 playbook 与验收 skill 各有一份 | **以 playbook 为准**；验收 skill 只引用 |
| 编号 `R-XX` / `RQ-001` / `R-xx` 三套 | **统一 `R-xx`** |
