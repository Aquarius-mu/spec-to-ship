# 开发踩坑规则清单

> 用法：开工前扫第 1、2 节；写协议前扫第 3 节；实现中扫第 4–7 节；交付前扫第 8–9 节。
> 每条规则都来自真实返工；**没有真实依据的规则不许写进来**。

---

## 1. 十条铁律

1. **先读原文，再动手。** 需求文档是唯一权威；skill、记忆、参考代码只决定"怎么做"，不决定"该不该有"。
2. **禁止用代码现状反推需求。** 代码没写不等于需求没有；代码写了不等于需求要求。
3. **禁止凭片段推断。** 规则、交互、边界、结算、奖励、红点、日志逐节读完再写码。
4. **禁止重复问。** 文档已写、用户已答、skill 已记的问题，先查再问；七路检索没跑完不许提问。
5. **接线不等于实现。** 注册 handler、加字段、调函数都不算；打开实现确认语义覆盖范围。
6. **没有证据不算完成。** 回包、状态、推送、日志至少三路之一可复现；无证据就标 `[推断]`。
7. **先判定后写入。** 任何比较当前状态的分支，禁止先覆盖再比较。
8. **配对操作必须成对。** 做一步就写撤销/退款/去重/清理，写不出失败路径就不算完成。
9. **单一事实源。** 编码、排名口径、展示快照、结算键只允许一个生成函数，第二处手写即缺陷。
10. **未外放不写兼容。** 不做迁移、补档、老存档修补；协议 tag 可连续压实。

---

## 2. 需求与文档

### 2.1 读案五类载体，缺一即未读完
正文（含 callout、折叠、删除线）、内嵌表/Base、画板/画格、评论区、修订历史。每类都要留证据；读不到的写原因，不许装作读过。

### 2.2 高频读案错误
- 漏画板/内嵌表/评论/修订。
- 把删除线当有效需求。
- 臆想配置/伪需求（"按经验应该有"）。
- 把参考实现当需求。
- 把空章节当"没有要求"（应记为缺口）。
- 不识别内部矛盾（正文 10% vs 表里万分比 100）。

### 2.3 合格案子应包含的章节
0 载体与版本清单 → 1 概述/玩家路径/端客户端边界 → 2 时间轴与周期 → 3 组织关系 → 4 成长系统 → 5 核心玩法 → 6 道具 → 7 奖励/邮件/补发 → 8 排行榜 → 9 消息协议 → 10 配置表 → 11 GM/日志/引导 → 12 异常与边界 → 13 已废弃需求 → 14 内部矛盾与待确认 → 15 客户端职责清单 → 16 可机械判定的验收标准。

### 2.4 契约三方对齐
文档、客户端、配置表的**索引基准（0 起/1 起）、周期、命名、枚举、号段**逐项断言。

### 2.5 需求语义必须钉死
- 状态机要给完整状态迁移表：时间基准、GM 跳转后的对齐规则、跨期清理。
- 计数口径写清"何时算一次"：发起时还是完成时；当日重复是否算新一次。
- 奖励对象按分区还是单服写明。
- 字段命名要能区分同类功能。
- 错误码必须对应业务，不能复用无关功能的码。
- 不擅自加阶段/字段：用户没写的时间点、计数字段一律不加。

## 3. 协议与消息

- 先问"能不能不开新消息"；查询挂状态、同界面 `iType` 合一、对偶操作 `iOper` 合一。
- 客户端能算、能查表、能查榜的字段一律不下发：即将开始标记、总数、奖励预览、排行详情、上限值、未领计数。
- 公共协议目录只放客户端要消费的；服务端自用放内部数据结构目录。
- **CS 必回且仅回一条 SC**。框架已回错误又手工回一次 = 重复回包。
- **全分支都要回**：未配置、空缓存、异常、重复请求，每个分支恰好一条 SC；空回包默认按 P0 查。
- 错误通道二选一：`return 非 0` 交给框架，或 handler 自己回 SC。
- **push 与状态一一对应**：写一条 push 就写一条对应状态字段；只靠 push 时离线玩家看不到。
- 状态包只放本进程内存零成本拿到的数据；跨进程/排序/聚合字段走查询消息。
- 已落盘结构 tag/类型不可改；要换结构新开 tag 并做迁移；未外放才可压实。
- IDL 没有前向引用；被引用 struct 必须先定义。
- 删除字段必须全库 grep 并同步改 C++ 赋值处。
- 协议号动手前 grep 全库找真正空闲段，生成器给的号段常撞车。

## 4. 状态、推送与生命周期

- **状态四联动**：改缓存 = 写字段 + 标脏 + push + 日志，缺一不可。
- **缓存更新不等于消息送达**：只 commit 本地投影就 return = 功能没完成；推送要覆盖在线/离线、新服/老服、跨服、重登。
- **幂等 `continue` 跳过的块里不能放配对清理**：晚到的旧回流会擦掉新占位。
- 活跃期到期必须清理队列/队伍/额度；重启后活动起点丢失会让过期判定失效。
- **先判定后写入**：先写新状态，后续 `if (state == 目标) return;` 恒成立，整段副作用变成死代码。
- **常驻 UI 必须有首屏来源**：不能只靠 push；离线玩家靠登录/查询拉取。
- 状态必须定义完整生命周期：初始、正常变更、边界、失败回滚、离线、重登、重启、跨周期、并发、多入口。
- 展示快照逐字段做生产端↔消费端对账；只写不读就是死字段。
- 同一语义多份实现会漂移：轮次编码三处手写、排名下标 +1 与同分同名次各写一套。
- 排行榜走通用榜；奖励预览客户端读表；红点客户端自己算。
- **同一事实多副本必须显式定时效**：Live / Snapshot / Derived 三选一；每个副本写清权威源、采样时点、刷新/失效触发、消费口径；展示与结算必须同一份、同一时点。
- **快照没有刷新触发就是永久冻结**。
- **派生属性先写齐再展开**：加成必须在组装战斗数据之前写入，否则百分比不展开；且不能同时写两个容器，否则双算。
- **用户说"和参考实现保持一致"时，抄的是它的完整链路**：写入、推送、离线补课、跨服透传、客户端结构五处都要对齐，不是只复制字段名。

## 5. 配置、表与 GM

- 配置以策划表为准；文档没写的 key 标注让策划补，**禁止编默认值兜底**。
- 配置表缺键可能导致**整表加载异常**，不是单值错误；先校验表版本与缺键。
- 索引基准、单位、0/空语义逐列确认：0 = 不限还是 0 次；存秒/配小时/显示小时。
- 打表：loader 每个字段必须在映射配置里有对应项，否则不生成该列。
- 活动配置只加需求明确列出的字段，禁止脑补分组/包装层。
- GM 输出复用真实协议结构，不要用旧结构拼包。
- GM 危险操作必须显式目标（如调时间只影响指定服），默认拒绝。
- 错误码续编该活动已有号段，不另起新段。
- 日志字段数量/顺序/类型必须与日志定义严格一致（字段错位会坏线上日志）。
- 日志语义逐条核对：胜负写反、倍率填单价、排名填字符串。

## 6. 跨服、并发与幂等

- **先定层再取数**：网关 / 跨服(owner) / 归属服 / 驱动服，分区号不等于归属服号。
- **跨服只走消息，不跨库直写**：两个业务域各有自己的共享存储，不要跨域直写。
- **跨服禁止本区兜底**：找不到快照用本区角色兜底，跨区场景全错。
- **跨服视图禁止裁剪战斗快照字段**：裁掉战斗上下文 → 空数据。
- 跨服 key 由不可变身份唯一构造；可变维度（session/赛季）不进主键。
- **有 key 必有出口**：以自增序号为 key 的上下文容器，只在回包 erase；离线实例不回包 → 必须加超时清理。
- 同型泄漏修一处必须扫全部同类（按"容器 + key 来源 + 删除点"枚举）。
- 调度活性：额度 0、超时、放弃、重试耗尽都必须回收并推进；提前 return 跳过超时回收 → 在途槽位永久卡死。
- 修复要覆盖全部阶段：只改入口不覆盖双败/淘汰赛 = 白修。
- 选主/租约必须有过期；永不过期水印 + 两套让位判据 → 两台同时让位永久停摆。
- RPC 线程不碰主线程分区状态；整表拷贝 + 并发写入会崩。
- 清理必须按分区 key 隔离，A 区缓存不能清全局。
- 测试矩阵：2 网关 × 2 跨服 × 多分区 × 接管切换 × 离线回包；每分区恰有一个存活 owner。

## 7. 发奖、扣费与结算

- **先校验后落库**：先持久化再校验，失败不回滚 → 重复数据泄漏到跨服。
- **先扣费、再发奖、失败回滚**：扣了道具、发奖失败直接返回 = 玩家重试再扣一次。
- **先写幂等键再发奖**；键必须含对象 id + 轮次 + 事件 id，只用事件 id 会撞号吞奖。
- 幂等键还要带活动/赛季；旧 key 必须过期清理；ready 标记的写入侧与读取侧必须对称。
- 失败不置终态；先置去重位再发邮件、丢弃发送返回值 = 永久漏发。
- 一份奖励一个状态机；所有出口（按钮、弹窗、邮件、补发、跳轮）共用置位。
- 旧期实例判空必须 `continue`；否则遍历时会全量扣除玩家当前持有量。
- 重启跨过整个结算期必须补结算；无榜分支不能永久标记已领。
- 待发队列不能在回包前清空；投递要有 ack 或补投。
- 扣费与退款必须对称：折扣、税费、消耗规则逐项对齐。

## 8. 发布与运维

- 批处理脚本每一步检查退出码，失败 fail-fast；不查退出码仍打印 success 是经典事故。
- `yes |` 管道会死锁：主脚本退出但子进程持有读端，后续步骤全不执行。
- 后台任务用 `nohup` 时，停止要能杀掉整个进程链，不能只断 SSH。
- 发布前确认"每区一次"还是"每机一次"；分发粒度错会漏包。
- 源码修了不等于线上生效：源码已修、未编译/未发布 = FAIL。
- **禁止直接覆盖线上脚本**：先备份、先 dry-run、确保可回滚。
- **编译归属要事先约定**：很多团队要求用户自己编译，AI 只负责改码与验证。
- 验证先确认二进制含该命令（GM 返回"命令不存在"时先查部署，不是先改代码）。
- 文件漂移要重核：审查期间源码可能被改，行号会漂。
- 审查行号用 diff 新侧；本地工作副本滞后会造成错位。

## 9. 证据与交付纪律

- **全量不是抽样**：要求"所有玩家/所有轮次/全量"时，抽样结论会被直接打回。
- **同一问题被指出第二次就停止点修**：回文档和参考实现做全链路对照，提炼成可机械检查的规则；只修当前一例 = 下一例必错。
- **看过程，不看头尾**：复盘必须从报障 → 定位 → 修复 → 验证完整走一遍；只看结论会漏掉"修复引出新 bug"的链条。
- **大案增量落盘**：每 20 条需求写一次文件；"读完全部再一次性生成"极易超时。
- **评论优先于正文**：评论出现"删掉/改成/应该是"时按最新口径实现。
- 修一个功能要读**该需求单全部提交、全部调用方、全部部署服务器**，不能只看最近 diff。
- 任何"全部/所有"结论必须给覆盖范围、总数、时间区间、样本外说明。
- 交付三件套：覆盖表（需求 → `file:line` → 结论）、待外部输入清单、未验证项及原因。
- 说"完成"前必须：编译通过（或如实说明用户执行）、关键回包/日志实测、P0 清零。
- 归责必须带证据链：配置缺失先查表键与最近提交（提交号/作者/时间），不默认归某个人。
- 用户口头澄清效力高于文档字面，但必须写进已决台账并标日期/适用范围。
- 文档改了要回写；代码与文档不一致时给证据，不猜。

## 10. 工具与协作

- **编辑三查**：先读再改；遇 `not read` / `modified since read` / `string not found`，重新读并复制精确原文，不盲重试。
- **路径三查**：只用工作区内绝对路径；读、登记、删除前先确认存在；不登记临时目录或未生成产物。
- **大文件分段**：超过上下文预算用 `offset/limit` 或搜索，不整文件读。
- **搜索纪律**：搜索必须带目录/glob，排除构建产物与缓存目录；超时意味着缩小范围，不是重复同一条搜索。
- **长任务**：超过 2 分钟用后台任务 + 条件轮询；禁止 `sleep` 死等、禁止重复整仓扫描。
- **Windows 环境**：注意 `python` vs `python3`、`PYTHONIOENCODING=utf-8`、路径分隔符。
- **文档 CLI**：先看 `--help`；不臆造 SDK 参数。
- **后台任务**：保存任务 id；只停自己拥有的任务；停止前查状态；不跨会话复用 id。
- **命令与进程**：先 `command -v` 检查依赖；不按进程名批量 kill，不删保护路径。
- **破坏性操作**（改文件、删配置、停服、改环境）先确认。
- **子代理**：输出必须完整 schema + 计数对账；截断即失败。
- **skill 质量**：精简、母语中文、不写死环境参数。
