# 游戏功能开发通用手册

> **踩坑知识库**：
> - [`references/bug-patterns.md`](references/bug-patterns.md) —— **按“bug 怎么一步步发生”组织**：8 类发生链条 + 每类防呆规则 + 交付前 12 问。开工前先扫。
> - [`references/lessons.md`](references/lessons.md) —— 规则清单版：10 条铁律 + 分主题高频缺陷 + 证据锚点。**§4 含"同一事实多副本 + 时效语义"**，遇到“客户端看到的不是服务器算的”“改了没生效”“详情一直空”“加成没算进去”先读。

> 适用：任何有客户端-服务端交互、有多进程状态、有玩家可见反馈的功能。
> 来源：一个大型活动功能的真实验收数据（一批真实验收记录）与 数十个版本的协议变更史。
> 目标：把"验收时才发现"变成"开工前就写下来"。
>
> **全流程串联见 [`PIPELINE.md`](PIPELINE.md)**：从飞书案子到交付，每一步用谁、产出什么、什么算过了。
> **什么时候用哪个 skill 见根目录 [`README.md`](../../README.md)**：六个 skill 的分工、边界与重叠归属。

## 0. 先记住三条

1. **动作先于消息**：先定义"玩家能做哪些不可再分的动作"，再定义消息。跳过错这一步，消息一定反复改。
2. **契约先于代码**：协议是一份有版本的契约，不是代码写完后的说明。文档与 IDL 必须能机械对账。
3. **没写进表的状态就是没实现**：初始、离线、重登、重启、跨周期、失败回滚——不写出来，代码就不会有。

## 1. 开工前六张表（含表 0，缺一不许写代码）

### 表 0：副本谱系与时效契约（先填这张）

同一个业务事实往往不止一份：Role Cache、Redis、跨服快照、协议结构、战斗 camp、客户端展示缓存。先给每个字段定性 **Live（实时）/ Snapshot（事件快照）/ Derived（可推导不存）**，再填：

| 事实 | 权威源（唯一） | 副本落点 | 写入者 | 采样时点 | 刷新/失效触发 | 消费者与口径 |
|---|---|---|---|---|---|---|
| | | | | | | |

**硬规则**：
- 一份权威源，其余都是副本；每个副本必须写清刷新/失效责任——没有触发条件的快照 = 永久冻结。
- **展示与结算必须同口径**：禁止“客户端看占格快照、战斗用实时值”。
- 派生值（属性/战力/血量）的**加数必须先写齐，再展开/汇总**，写晚了加成静默丢失。
- 反模式与机械核对见 [`references/bug-patterns.md`](references/bug-patterns.md) §2.5 副本漂移；长期规则见 [`references/lessons.md`](references/lessons.md) §4 状态、推送与生命周期。

### 表 1：状态生命周期矩阵（挡掉最多 bug）

对每个会变的状态字段填满：

| 时刻 | 谁写 | 写什么 | 谁读 | UI 怎么显示 | 无值/失败怎么办 |
|---|---|---|---|---|---|
| 初始（新号/新赛季/首次解锁） | | | | | |
| 正常变更 | | | | | |
| 边界（0/上限/上限±1/跨天） | | | | | |
| 失败回滚 | | | | | |
| 离线变更 | | | | | |
| 重登回填 | | | | | |
| 重启恢复 | | | | | |
| 跨周期重置/结转 | | | | | |
| 并发/重复点击 | | | | | |
| 多入口一致性（列表/详情/战报/多视图） | | | | | |

**判据**：写"没考虑"= bug 预定单；写"不适用"必须给理由。

### 表 2：ID 域表

| 字段 | 是哪种 id | 范围 | 谁能填 | 会被当成别的 id 吗 | 用下标代替了吗 |
|---|---|---|---|---|---|

**硬规则**：
- 跨函数传递的 id 带命名空间后缀（`iMineId`/`iEventId`/`iCellIndex`），禁止裸 `iId`。
- 同一结构体不允许两个语义不同的 `iId`。
- **用数组下标当业务身份是最高危写法**：数组一压实/重排就错位。
- 同一字段在不同分支代表不同 id 域时，拆成两个字段。

### 表 3：上限表

| 上限 | 来源 | 校验入口 | 客户端口径 | 等于时 | +1 时 | UI 反馈 |
|---|---|---|---|---|---|---|

**硬规则**：
- 上限只在服务端算一次，客户端只做展示；客户端不得自己推导上限。
- 所有"可操作/不可操作"判断来自同一函数，禁止两个入口各写一份。
- 边界必须覆盖：0 / 1 / 上限-1 / 上限 / 上限+1。

### 表 4：变更→推送表

| 状态字段 | 变更点 | 推给谁 | 推什么包 | 失败重试 | 离线补偿 | 幂等键 |
|---|---|---|---|---|---|---|

**硬规则**：
- 每个"写"必须对应一个"推"；只写不推 = 玩家看不到。
- 失败路径也要推（否则 UI 停在旧值）。
- 离线玩家靠首屏/重登拉取，不能只靠 push。
- 同一事件多个消费入口必须带幂等键。

### 表 5：消息契约表

| 玩家动作 | 请求消息 | 回包 | 推送 | 唯一键 | 失败码 | 离线补课 |
|---|---|---|---|---|---|---|

**硬规则**：
- 一条消息只对应一个动作；一个动作只有一个请求。
- 每个推送写清幂等键 + 补课通道。
- 每条消息写清"客户端不实现会怎样"。

## 2. 协议契约管理（文档 ↔ IDL 必须机械对账）

### 2.1 权威源

- **IDL 是唯一权威**；文档是它的投影。
- 文档里的每条消息、每个字段、每个号，必须能从 IDL 导出。
- 人工同步必然漂移——这不是态度问题，是机制问题。

### 2.2 机械对账脚本

```bash
python "<skills>/game-feature-playbook/scripts/audit_message_contract.py" \
  --idl-dir "~/work/main/Common" \
  --doc "<消息指南.md>" \
  --prefix Cmd_Act_Example \
  --show-missing
```

输出两类必查项：

- **FAIL 幽灵项**：文档写了、IDL 没有 → 客户端照文档实现必然错。
- **WARN 遗漏项**：IDL 有、文档没提 → 客户端可能不知道这个字段存在。

真实案例（2026-10 用该脚本跑某历史活动消息指南）：

- 幽灵消息 `Cmd_Push_Act_Example_MapStatusChange`（20590）——代码里根本不存在，且 20590 实际是另一条消息。
- 幽灵字段 `stOuterMineResult`、`iMaxTeamNum`、`stGarrison`、`iMilitary`、`iActualInvestSeconds`。
- 遗漏字段 `TerminateCollect_CS.iCellIndex`——**直接导致"取消 A 却取消 B"**。
- 遗漏整条消息 `BackToOuterMap_CS/SC`（71123/71124）——离线补偿通道，客户端不知道要发。

### 2.3 删改规则

- **删字段留墓碑**：IDL 注释写 `// tag2 已废弃(rXXXXX)，禁止复用`；文档标"已删除，勿实现"。
- **号段复用必须记录**：原用途 → 新用途 → 时间。
- **语义变更单列**：如 `long→uint`、字段含义变化，必须出"破坏性变更"清单并通知客户端。
- **IDL 与引用它的 cpp 原子提交**；提交后在干净检出上再编译一次。

### 2.4 字段语义只写一次

- 容易歧义的字段（格位下标、索引、版本号）在 IDL 注释里写清：**物理格号 / 数组下标 / 逻辑 id**。
- 其他文档引用它时只链接，不重新解释——二次解释必然产生矛盾。

真实案例：同一份消息指南里，2.2 说 `iCellIndex` 是"物理格位号，压实后数组下标≠格号"，8.5 却说 `iTargetCellIndex` 是"紧凑下标，与转码 1:1"。两处直接冲突，客户端按 8.5 实现就会顶替错人。

## 2.5 六条代码结构不变量（比表更根本）

对一个真实服务端做完结构审查后，43 条问题归并成 6 个根因。任何有"跨进程 + 存档 + 两阶段操作 + 推送"的功能都会长出这 6 类，直接用不变量压住：

| # | 不变量 | 规则 | 不满足会长出什么 |
|---|---|---|---|
| I1 | **错误 ≠ 空** | 外部读取返回 `Ok / NotFound / Error` 三态；Error 禁止走创建/删除/覆盖分支 | 读失败被当成"未匹配"→删光数据；被当成"未入图"→一人两图；NoData 被当成新图→覆盖活档 |
| I2 | **一个 key 只有一个来源** | 存储地址由不可变身份经唯一构造函数生成；可变维度（session/版本）不进主键 | 同一对象裂成多份档；两个进程各拼一套 key；读 A 写 B |
| I3 | **变更必须带票据** | 两阶段操作提交时校验 `reserveId + 目标身份 + 版本`；不符则拒绝，不静默改目标 | 迟到的结果作用到新对象上；用旧快照的数据结算当前对象 |
| I4 | **交付必须 at-least-once** | 先入队/落盘再回包；消费方显式 ack；幂等键覆盖完整域 | 回包前清空→永久丢；重复投递→重复发奖；幂等键缺维度→跨图误判 |
| I5 | **状态只有一个写入口** | 统一 `resolveCell/commitCell`；版本号由写入口递增；禁止外部直接改容器 | 下标/物理号混用→操作错对象；版本漏加→增量同步失效 |
| I6 | **失败必须可恢复** | 每个失败分支三选一：重试 / 进 pending / 告警；先完成所有可失败步骤再回包 | 一次请求两条回包；失败后状态不回滚；活动结束后补偿入口失效 |

代码草案见 `example-s3-dev/references/structural-hardening.md`（同一套结构可直接搬到别的玩法）。

**落地顺序**：先做 I1（只改语义、风险最低）→ I2/I3/I4（改协议与存储，需配套发版）→ I5/I6（大改，新赛季做）。

## 3. 缺陷分类学（用来预测新功能会怎么坏）

| 类型 | 典型表现 | 前置对策 |
|---|---|---|
| 状态没定义完整 | 首次解锁显示"已满"；重登不弹窗；跨周期不结转 | 表 1 |
| ID 域混淆 | 取消 A 误取消 B；第二排头像错；按周取错配置 | 表 2 |
| 上限口径不一 | 5/4 还能加；未到上限却打不了 | 表 3 |
| 状态同步缺失 | 改完不刷新；多视图红点不一致；排行榜要重启 | 表 4 |
| 副本/时效口径不一致 | 展示与结算各用一份；快照不刷新；攻守两侧实时/快照混用；加成写晚没展开 | 表 0 |
| 战报多源不一致 | 战力与阵容不符；缺公会；秒杀战报显示打 NPC | 战报生成点清单 |
| 消息契约漂移 | 幽灵字段；漏字段；错号；语义矛盾 | 表 5 + 对账脚本 |
| 配置多消费方 | 只发一边，另一边读默认值 | 消费方清单 + 版本哈希 |
| 失败路径静默 | 查不到=不存在；读失败=建空图 | 失败矩阵 + 失败注入 |

## 4. 开发中与提测前

### 开发中

- 每加一个跨模块消费/下发的字段或状态，回填表 0（权威源、副本落点、采样时点、刷新/失效触发、消费口径）。
- 每落一个写操作，回填表 1、表 4。
- 每加一个字段，回填表 2、表 5，并写 IDL 注释。
- 每加一个上限，回填表 3。
- 每加一个推送，写幂等键与补课通道。

### 提测前自测（把 QA 会问的先自己打一遍）

**初始态**：新号/新赛季/首次解锁显示正确；未解锁时相关入口隐藏；解锁链前置生效。

**边界**：0 / 1 / 上限-1 / 上限 / 上限+1；刚好跨天/跨周/新一轮；剩余时间 < 当天剩余。

**失败**：资源不足、兵力不足、被抢先、目标失效 → 回滚 + 提示 + 刷新。
客户端传来的非法数据一律拒，不代洗——缓存清洗逻辑别套到请求校验上。

**生命周期**：在线变更立刻可见；离线变更重登可见；重启数据完整；跨周期正确。

**并发**：狂点；两个入口同时操作；取消 A 不影响 B。

**一致性**：列表与详情、多视图、客户端与服务端、战报与排行榜；
派生字段（攻守方、组别、名次、胜负）要逐条自洽，同一数值只允许一个来源。

**协议**：用对账脚本跑一遍，零幽灵；抓包验证关键字段语义（尤其下标/索引）。

## 6. 更深的一层：为什么"定义"总是被跳过

多数团队不是不知道要写这些表，而是**默认"先写起来，边写边改"**。
这在单机、单进程、无状态的功能上勉强可行；但在多进程、有存档、跨周期、客户端强依赖的功能上，边写边改的代价会以指数放大：

- 每改一次消息，客户端要重接一次；
- 每改一次字段语义，历史数据要迁移一次；
- 每漏一个时刻，就在验收时多一条 bug；
- 每错一个下标，就在线上多一批"操作了别人"的客诉。

所以真正的分水岭不是"仔细不仔细"，而是：

> **你是在设计一个系统，还是在迭代一段代码？**

设计系统，就必须先有状态、有契约、有边界；
迭代代码，只会得到"能跑，但每个角落都有例外"。

系统里最容易被跳过的不是"字段"，而是"同一件事的多个副本之间的关系"。所以比"这个字段放哪"更深的一问是：

> **这一个事实，在我的后端里一共有几份？每份的采样时点与刷新责任是什么？展示和结算用的是不是同一份？**

这三句答不上来，加多少字段都只是把 bug 往后推（见表 0）。

三期（或任何新功能）开工前，先问一句：
**"如果明天换一个人接手，他只看这些表（含表 0），能不能把功能实现得和我一样？"**
能，才是设计完成；不能，就还在迭代代码。
